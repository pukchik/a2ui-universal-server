# Стек и план реализации

Документ описывает технические решения для первой версии из [README.md](README.md). README объясняет идею проекта и взаимодействие его частей; здесь зафиксированы контракты, состояния, способы реализации и проверки. Кода пока нет; выбор библиотек не означает, что интеграция уже проверена.

## Базовое решение

**TypeScript, Node.js LTS, Fastify, PostgreSQL, Drizzle, HTTP + SSE.** Один процесс сервера обслуживает API и управляет ограниченным числом дочерних процессов Codex CLI. PostgreSQL хранит команды, запуски, историю и состояние UI. Первый адаптер использует `codex exec`; инструменты проекта предоставляются через внутренний MCP endpoint. Эталонный клиент использует Vite, Lit и официальный A2UI-рендерер.

В первой версии не требуются Redis, BullMQ, отдельный worker, Kubernetes или S3. Незавершённые задания уже представлены строками в PostgreSQL. Дополнительный брокер добавляется только вместе с задачей распределённого исполнения и измеримой необходимостью, а не как условие первого запуска.

## Проверка совместимости перед реализацией ядра

Первый технический шаг — небольшой интеграционный пример, который доказывает прохождение сообщений через Codex CLI, MCP и выбранный рендерер. Он должен снять ограничения внешних библиотек до разработки хранения и публичных пакетов.

| Элемент | Зафиксированное решение | Что ещё нужно проверить |
| --- | --- | --- |
| A2UI | Протокол 0.9.1 | Официальные JSON Schema и настройки Ajv |
| Рендерер | Официальный `@a2ui/lit`; кандидат — 0.13.0 | Наличие устанавливаемого выпуска, его зависимости и работа с 0.9.1 |
| Каталог | Basic Catalog для 0.9.1 | Точная версия/ревизия исходников, URI каталога и хеш содержимого |
| Агент | Codex CLI через `codex exec --json` | Версия CLI, модель, авторизация, JSONL, итоговая схема и отмена процесса |
| Инструменты | MCP по Streamable HTTP внутри установки | Совместимость SDK и CLI, полномочия запуска, недоступность обходных инструментов |
| Контекст | Новая ephemeral-сессия Codex на каждый запуск | Передача истории и каталога; отсутствие зависимости от `resume` и локальной истории CLI |

Число `0.13.0` взято из [package.json официального рендерера](https://raw.githubusercontent.com/a2ui-project/a2ui/main/typescript/renderers/lit/package.json), проверенного 21 октября 2026 года. Это версия исходного пакета, а не доказательство публикации или успешной установки. [Матрица A2UI](https://a2ui.org/reference/renderers/) указывает поддержку 0.9.1 для Lit. Оба факта требуют проверки вместе на установленном выпуске.

При проверке локальной установки 21 октября 2026 года доступны Codex CLI `0.163.0`, `exec --json`, `--ephemeral`, `--output-schema` и чтение промпта из stdin. Проверены версия и справка CLI; реальный запрос к модели не запускался. Эта версия — кандидат для первого интеграционного примера.

Результат интеграционного шага — точные версии зависимостей в package.json и lockfile, версия бинарного Codex CLI в образе, модель и профиль запуска в конфигурации примера, зафиксированные официальные схемы и каталог с происхождением, а также воспроизводимый браузерный сценарий. Если нужен пакет из исходников, закрепляется конкретный commit; плавающая ветка `main` не является зависимостью релиза. Неопубликованный агентский SDK A2UI не требуется для первой версии.

Минимальная проверка: создать поверхность, показать текст и форму, отправить действие, получить tool result, обновить данные, удалить поверхность и восстановить её из сохранённого состояния. Проверяется также некорректное сообщение. Демонстрационный сценарий использует небольшой набор компонентов Basic Catalog; заявлять полную совместимость всех возможностей каталога только по этому примеру нельзя. Неподдержанные возможности должны явно отклоняться до публикации UI.

## Границы модулей

```text
apps/
  server/
    src/
      http/          # Маршруты, OIDC, сессии, SSE
      execution/     # Выбор запусков, лимиты, отмена
      storage/       # Drizzle, SQL, миграции
      adapters/      # Codex CLI и тестовый адаптер
      mcp/           # Внутренний endpoint и полномочия запусков
      tools/         # Реестр, шлюз, демонстрационные инструменты
  web/               # Lit-клиент и оболочка диалога
packages/
  contracts/         # Схемы HTTP, событий и контракт адаптера
  core/              # Переходы состояния и применение A2UI
  client/            # HTTP, SSE, дедупликация событий, восстановление
deploy/              # Compose и пример конфигурации
```

Это план структуры, каталоги ещё не созданы. Отдельные публикуемые adapter-sdk, storage, mcp и testing добавляются только при появлении потребителей. Changesets потребуется при публикации пакетов; на первом этапе достаточно согласованной версии приложения и API `/v1`.

Ядро не зависит от Fastify, Codex CLI или DOM. Оно получает проверенный контекст пользователя и использует интерфейсы хранения и инструментов. HTTP-маршрут проверяет вход и вызывает операцию ядра. Процесс Codex не получает доступ к SQL и HTTP-ответу клиента.

## Основные сущности

| Сущность | Назначение |
| --- | --- |
| Проект | Настройки установки: адаптер, модель, каталог, инструменты и ограничения |
| Диалог | Принадлежит пользователю; содержит историю, закреплённую конфигурацию и состояние UI |
| Команда | Запрос клиента с `commandId`; повтор команды не создаёт второй запуск |
| Запуск (`run`) | Одна принятая команда, выполняемая агентом, с отдельными статусом и лимитами |
| Вызов инструмента | Отдельная операция внутри запуска с ID, аргументами, результатом и статусом |
| Состояние UI | Поверхности A2UI, компоненты и модели данных, собранные из принятых сообщений |
| Событие | Сохранённое изменение с порядковым номером `seq` внутри диалога |

История, состояние UI и техническое состояние адаптера разделены. В первой версии история и UI переживают перезапуск сервера; незавершённый запуск агента автоматически не продолжается.

## HTTP-контракт

| Метод и маршрут | Назначение |
| --- | --- |
| `POST /v1/dialogs` | Создать диалог с закреплённой конфигурацией |
| `GET /v1/dialogs/:id` | Получить метаданные и текущий статус |
| `GET /v1/dialogs/:id/messages` | Прочитать историю с пагинацией |
| `GET /v1/dialogs/:id/snapshot` | Получить согласованный снимок UI и курсор событий |
| `GET /v1/dialogs/:id/events?after=<seq>` | Подписаться на события после указанного номера |
| `POST /v1/dialogs/:id/messages` | Принять сообщение и создать запуск |
| `POST /v1/dialogs/:id/actions` | Принять действие UI и создать запуск |
| `POST /v1/dialogs/:id/runs/:runId/cancel` | Отменить конкретный запуск |

Маршруты описываются OpenAPI. В первой версии используется same-origin браузерный клиент с серверной сессией. Все POST требуют CSRF-защиты и `commandId` в теле. Создание диалога возвращает `201`, принятие запуска — `202` с `commandId`, `dialogId`, `runId`; отмена возвращает `200` с результатом операции. В момент ответа запуск уже может выполняться: актуальный статус читается из событий или состояния диалога.

Форма ошибок: `{ "error": { "code": "stale_ui", "message": "...", "details": {} } }`. Код стабилен, текст предназначен человеку. `409` используется для конфликта команды, занятого диалога, устаревшего UI и несовместимой конфигурации клиента; `422` — для неприемлемых аргументов; `429` — для превышения лимита. Неавторизованный запрос получает `401`; отсутствие доступа к конкретному диалогу возвращается как `404`, чтобы не раскрывать его существование. Проверка доступа выполняется и при повторе команды.

Пример тела действия — оболочка собственного API; содержимое `action` приводится к выбранной версии A2UI:

```json
{
  "commandId": "c3dc0867-ae03-4dc8-a4dc-5f951e942fe6",
  "uiRevision": 4,
  "action": {
    "surfaceId": "products",
    "componentId": "details-lamp-1",
    "name": "show_product",
    "context": { "productId": "lamp-1" }
  }
}
```

Контекст действия считается пользовательским вводом. Сервер сверяет компонент и действие с сохранённым UI, ограничивает размер и проверяет аргументы. Идентификатор товара из формы не заменяет проверку доступности товара в инструменте.

## PostgreSQL и атомарность

Основные таблицы: `projects`, `users`, `sessions`, `dialogs`, `messages`, `commands`, `runs`, `tool_calls`, `dialog_ui`, `dialog_events`. OIDC-пользователь определяется парой issuer и subject. Проект в первой версии один, но принадлежность объектов хранится явно. Пользователь владеет диалогом; доступ внутри проекта не означает доступ к чужой истории.

Состояние UI и полезная нагрузка событий хранятся в JSONB. ID, владельцы, статусы, порядковые номера и ссылки остаются отдельными колонками. Внешние ключи и ограничения БД выражают инварианты, а не только типы TypeScript.

Принятие сообщения или действия выполняется одной транзакцией:

1. Проверить пользователя и доступ к диалогу.
2. Найти принятую команду по `(project_id, user_id, command_id)`. При совпадении типа, ресурса и хеша нормализованного тела вернуть сохранённый ответ; при различии вернуть `command_conflict`.
3. Заблокировать строку диалога, проверить отсутствие незавершённого запуска; для действия сверить ревизию и допустимость UI.
4. Записать команду, сообщение/действие, запуск `queued` и событие принятия. Сохранить исходный HTTP-результат команды.
5. Зафиксировать транзакцию и вернуть ответ клиенту.

Конкурирующие запросы с одинаковым `commandId` разрешаются уникальным ограничением и повторным чтением сохранённой команды. Нельзя превращать конфликт ограничения в `500`. Частичный уникальный индекс запрещает более одного `queued` или `running` запуска на диалог. Создание диалога вместе с его командой также атомарно и идемпотентно.

При занятом диалоге новое сообщение или действие получает `409 dialog_busy`; скрытой очереди сообщений внутри диалога нет. Отмена доступна и в этом состоянии. После отказа, не создавшего команду и запуск, клиент исправляет запрос и использует новый ID.

Повтор команды возвращает первоначальный результат принятия, а не повторяет бизнес-операцию. Хеш рассчитывается по нормализованным данным, а не по порядку ключей в исходном JSON. Принятые команды не очищаются, пока хранится диалог; автоматическое удаление истории в первую версию не входит.

Изменение UI блокирует строку диалога, проверяет активный запуск и поколение исполнения, применяет пакет к копии состояния, затем одной транзакцией сохраняет UI, увеличенную ревизию и событие. Выделение `seq` тоже происходит под этой блокировкой: порядок номеров должен соответствовать порядку фиксации событий. Статусы и текст публикуются по тому же правилу «сохранить, затем доставить».

Миграции выполняются отдельным шагом перед запуском приложения. Резервное копирование PostgreSQL включает историю, команды, UI и сессии; процедура восстановления проверяется до первого развёртывания с пользовательскими данными.

## Состояния и отмена

| Статус запуска | Значение | Допустимые переходы |
| --- | --- | --- |
| `queued` | Команда сохранена, выполнение ещё не началось | `running`, `cancelled` |
| `running` | Адаптер выполняет запрос | `succeeded`, `failed`, `cancelled` |
| `succeeded` | Обработка завершена успешно | Нет |
| `failed` | Ошибка, превышение лимита или прерывание при перезапуске | Нет |
| `cancelled` | Сервер принял отмену и закрыл запуск для новых изменений | Нет |

Терминальный статус не меняется. При гонке завершения и отмены побеждает первая зафиксированная транзакция; отмена уже завершённого запуска возвращает его существующий статус. Разрыв SSE не отменяет запуск.

После принятой отмены сервер запрещает новые вызовы инструментов и изменения UI этим запуском, передаёт сигнал адаптеру и освобождает локальные ресурсы. Уже начавшийся удалённый запрос может продолжиться и тарифицироваться провайдером. Отмена не означает отмену действий во внешней системе; изменяющих инструментов в первой версии нет.

Вызов инструмента проходит `running → succeeded | failed | cancelled`. Отмена запуска закрывает его незавершённые вызовы; поздние ответы не передаются в UI или следующий шаг агента. Поздний ответ может быть записан только как техническое диагностическое событие без изменения терминального результата.

После перезапуска сохранённые `queued` запуски могут начать выполнение. Запуски, оборвавшиеся в `running`, становятся `failed` с причиной `interrupted`; связанные незавершённые вызовы также помечаются прерванными. Автоматического повторения обращения к модели нет. Повтор по решению пользователя создаёт новую команду и новый запуск.

## Исполнение запусков

Фоновый цикл периодически выбирает `queued` запуски из БД с учётом глобального лимита. Принятие команды может дополнительно разбудить цикл, но потерянное уведомление не теряет работу. Захват запуска и перевод в `running` выполняются транзакционно. Перед вызовом провайдера проверяется, что запуск всё ещё активен.

Каждая попытка получает серверный идентификатор поколения. Запись UI, вызов инструмента и завершение разрешены только активному поколению в статусе `running`. Отмена закрывает запуск в БД до отправки сигнала адаптеру. Тот же транзакционный контроль не позволяет позднему результату изменить отменённый запуск.

Для первой версии допускается ровно один процесс сервера, управляющий исполнением; процессы Codex являются его отдельными дочерними задачами. Сервер удерживает PostgreSQL advisory lock на отдельном соединении; второй экземпляр не начинает обслуживание и исполнение. При потере соединения с блокировкой процесс прекращает приём команд и исполнение и завершает работу. Новый процесс после получения блокировки помечает старые `running` запуски как `failed/interrupted` до возобновления очереди. Этот механизм ограничивает первую установку одним экземпляром и не заменяет будущий распределённый lease.

Применяются настраиваемые ограничения: размер команды и результата инструмента, размер/число A2UI-сообщений, размер контекста, время запуска, число серверных вызовов инструментов и попыток исправления, число одновременно выполняемых запусков и ожидающих заданий на пользователя и установку. Стартовые значения фиксируются в конфигурации примера после интеграционной проверки. При переполнении очереди команда отклоняется до создания запуска.

При отмене адаптер останавливает группу процессов Codex: сначала штатным сигналом, затем принудительно после grace period, и ожидает завершения. До отправки сигнала ядро закрывает запуск и отзывает его MCP-полномочия. Шлюз инструментов и приёмник A2UI независимо проверяют состояние в БД. Автоматические повторы целого запуска после ошибки отключены. Внутренние шаги и сетевые повторы CLI не считаются полностью управляемыми сервером: жёсткие внешние границы — дедлайн процесса, объём вывода и число разрешённых вызовов MCP.

При штатной остановке сервер перестаёт принимать команды и начинать новые запуски, даёт активным завершиться в пределах grace period, затем закрывает оставшиеся как прерванные и освобождает ресурсы. Сохранённые `queued` остаются для следующего запуска сервера.

## Ответственность ядра и адаптера

| Ядро сервера | Адаптер |
| --- | --- |
| Проверяет доступ, принимает команды и управляет статусами | Преобразует контекст и инструкции в формат провайдера |
| Собирает контекст из сохранённых сообщений и актуального UI | Запускает Codex, внутри которого проходит цикл «модель → инструмент → модель» |
| Проверяет и выполняет инструменты проекта через единый шлюз | Подключает Codex к MCP, ведущему в этот шлюз |
| Проверяет A2UI, применяет его к состоянию и сохраняет события | Разбирает ответ провайдера и выдаёт полные сообщения A2UI и текст |
| Выдаёт ошибки валидации и ограничивает попытки исправления | Возвращает ошибку модели для одной разрешённой попытки исправления |
| Ограничивает время, вызовы инструментов, попытки исправления и объём данных | Останавливает процессы Codex и освобождает ресурсы |

Адаптер не записывает состояние диалога напрямую и не вызывает обработчики инструментов в обход шлюза. Инструменты Codex, позволяющие обойти серверный шлюз, отключаются в профиле запуска и проверяются интеграционным тестом. Загружаемые адаптеры и обработчики считаются доверенным кодом оператора.

Минимальный контракт адаптера содержит описание возможностей и операцию выполнения запуска. Во входе — `runId`, закреплённая конфигурация, подготовленный контекст, инструкции, каталог, описания инструментов, лимиты и сигнал отмены. Во время выполнения адаптер может передать текст, предложить пакет сообщений A2UI, вызвать инструмент и завершиться с результатом или ошибкой. Передача A2UI возвращает адаптеру результат проверки: пакет принят либо отклонён с описанием ошибки.

Для первой версии обязательны приём переданного контекста, выдача полных A2UI-сообщений и работа через шлюз инструментов. Потоковая выдача и фактическая остановка запроса провайдеру — отдельные возможности. Адаптер без потока выдаёт один итоговый пакет; отсутствие остановки не разрешает ему изменять отменённый запуск.

Каждый запуск начинает новую сессию `codex exec --ephemeral` с контекстом из PostgreSQL. `thread_id` CLI можно сохранить для диагностики, но он не заменяет ID диалога и не используется для `resume`. После ошибки или отмены следующая команда не продолжает скрытую историю с непринятыми результатами. Сервер не обрезает историю молча: превышение его лимита контекста даёт явную ошибку. Внутренние механизмы управления контекстом Codex остаются частью CLI и не являются серверной гарантией сохранения полного промпта.

Codex CLI — обязательный адаптер первой версии. Другие CLI и SDK могут добавляться позже, соблюдая те же границы: инструменты проекта проходят через сервер, состояние меняет только ядро.

## Адаптер и инструменты

Адаптер запускает Codex через `child_process.spawn` с массивом аргументов и передаёт инструкции, контекст и каталог через stdin. Командная строка из пользовательского текста не собирается. Для первой версии используется `codex exec --json --ephemeral`; итоговый ответ запрашивается через `--output-schema` и записывается в отдельный файл через `--output-last-message`. Эти возможности описаны в [официальной документации неинтерактивного режима](https://developers.openai.com/codex/noninteractive).

stdout разбирается как JSONL с ограничением размера строк; stderr отделяется от пользовательского ответа. События CLI используются для диагностики выполнения. Raw JSONL, рассуждения, команды и содержимое служебных событий не транслируются в браузер. Итоговый ответ принимается только после успешного завершения CLI, чтения его финального результата и серверной валидации. Выход с ошибкой, оборванный поток или отсутствие результата завершают запуск как `failed`.

Формат итогового ответа — объект с пользовательским текстом и сообщениями A2UI. Точная внешняя JSON Schema проверяется на закреплённой версии CLI; если полная схема A2UI не подходит для constrained output, сообщения передаются в строковом поле JSON и затем отдельно разбираются и проверяются ядром. `--output-schema` не заменяет проверку каталога и состояния UI. Первая версия Codex-адаптера публикует один итоговый пакет UI; JSONL-события CLI сами по себе не означают поток A2UI.

У операций адаптера ожидаемый смысл следующий:

| Операция | Результат |
| --- | --- |
| `describe()` | Возможности и версия контракта адаптера |
| `run(input, host, signal)` | Один цикл обработки команды; успешное завершение либо нормализованная ошибка |
| `host.emitText(text)` | Сохранение допустимого пользовательского текста |
| `host.proposeUi(messages)` | Атомарное принятие пакета либо структурированная ошибка проверки |
| `host.callTool(call)` | Проверка и выполнение вызова, возврат результата или ошибки |
| `host.beginRepair(error)` | Регистрация единственной попытки исправления и запрет инструментов до конца запуска |

Названия фиксируют границы интерфейса; точные TypeScript-типы и JSON Schema создаются в `contracts` на первом этапе ядра. Все операции host асинхронные. Адаптер обязан дождаться их результата перед завершением. Неисправленная ошибка UI и незавершённый вызов запрещают успешное завершение; исправленный пакет или обработанная ошибка инструмента с понятным ответом пользователю могут завершить запуск успешно. Метрики провайдера передаются отдельно от текста пользователя; неизвестные токены или стоимость не считаются нулём.

Контекст для нового запуска включает инструкции, закреплённый каталог, историю принятых сообщений и доступное актуальное состояние UI. У неуспешных ответов сохраняется отметка незавершённости. Технические логи и секреты в контекст не включаются. Отвергнутый пакет передаётся только в ограниченную попытку исправления, а не в историю следующей команды. Если подготовленный контекст превышает лимит, ядро завершает запуск с `context_limit`; пользователь начинает новый диалог.

При ошибке A2UI допускается одна попытка исправления в пределах того же запуска и общего дедлайна. Через `host.beginRepair` адаптер регистрирует попытку и запускает второй свежий `codex exec` с ошибочным ответом, описанием ошибки и необходимыми уже полученными данными. На этой попытке MCP-инструменты не подключаются, прежние полномочия отозваны; модель только исправляет ответ. Ошибка разбора JSON расходует тот же бюджет. В уже завершённый процесс CLI ничего не дописывается; новая команда пользователя при этом не создаётся. Повторная ошибка завершает запуск как `failed`.

Шлюз создаётся как серверный объект, привязанный к пользователю, проекту, запуску и его поколению. Эти поля не берутся из аргументов модели. Перед вызовом проверяются активность запуска, разрешения, `readOnly`, входная схема и лимиты. Вызов записывается до обращения к обработчику, результат — до MCP-ответа Codex. Повтор одного ID вызова с теми же аргументами использует сохранённый результат; с другими аргументами отклоняется. Неизвестный или ещё выполняющийся результат не запускается второй раз.

Обработчик получает проверенные аргументы и доверенный контекст пользователя. Результат проверяется по схеме и размеру. Таймаут, ошибка схемы и ошибка внешнего сервиса различаются. Вызовы исполняются последовательно в рамках одного запуска, даже если Codex отправил несколько MCP-запросов одновременно.

Тестовый адаптер реализует тот же контракт: он умеет выдавать заранее заданные пакеты, ждать отмены, имитировать ошибку и пытаться отправить поздний результат. Вторая реальная интеграция добавляется позже; универсальность пока подтверждается границей контракта, а не заявлением о поддержке всех SDK и CLI.

## MCP и среда Codex CLI

В первую версию входит внутренний MCP endpoint по Streamable HTTP на официальном TypeScript SDK MCP. Он публикует только разрешённые инструменты чтения и направляет вызовы в тот же `host.callTool`, который использует тестовый адаптер. Codex сам исполняет цикл обращения к MCP; наблюдение события tool call в stdout не является командой повторно выполнить инструмент.

Перед стартом CLI сервер выдаёт случайный короткоживущий bearer token, связанный в серверном хранилище с пользователем, проектом, `runId`, поколением и разрешёнными инструментами. CLI получает токен через переменную окружения, указанную в `mcp_servers.<name>.bearer_token_env_var`; токен не помещается в промпт или аргументы команды. Параметры HTTP MCP описаны в [документации Codex MCP](https://developers.openai.com/codex/mcp). Перед каждым вызовом сервер проверяет срок и активность запуска; при отмене, завершении или начале исправления токен отзывается. MCP session ID и переданный моделью `runId` не заменяют авторизацию.

Endpoint доступен только в приватной сети установки и обслуживается асинхронно, пока сервер ждёт CLI. Вызовы связываются с серверным ID операции; повтор одного MCP request ID в той же сессии не создаёт второе исполнение. Между разными сессиями совпадение request ID не считается повтором. При неожиданном интерактивном запросе разрешения запуск завершается диагностируемой ошибкой: браузерный интерфейс подтверждений в первую версию не входит.

Для процессов CLI задаётся отдельная среда: рабочая директория запуска, управляемая конфигурация и служебная авторизация Codex. Не наследуются личные настройки, MCP-сервисы, hooks, skills и файлы других диалогов с машины оператора. Профиль разрешает только MCP-инструменты проекта; shell, web search и другие обходные средства отключаются. В частности, документация описывает `features.shell_tool` и неинтерактивную `approval_policy = "never"`; точная конфигурация всех отключений закрепляется проверкой выбранной версии. [Справочник настроек Codex](https://developers.openai.com/codex/config-reference).

Используется read-only sandbox для инструментов, отдельная файловая область и минимальное окружение процесса. CLI не получает исходники сервера, SQL-credentials или Docker socket. Одна только read-only sandbox не является изоляцией чтения файлов: доступные монтирования, учётная запись процесса и сеть также ограничиваются. Разрешаются необходимые соединения Codex с провайдером и внутренним MCP endpoint; возможность произвольного выполнения команд не требуется этому приложению. Нельзя заменять эти ограничения флагом обхода sandbox.

Финальный файл и временные служебные данные изолированы по запуску и имеют ограниченные права. Supervisor развёртывания должен завершать всё дерево процессов при остановке или падении сервера, чтобы не оставлять осиротевший Codex. Эти свойства проверяются до заявления о готовности адаптера; отдельная распределённая система runner для первой установки не требуется.

## Состояние A2UI

Версия протокола, неизменяемая версия каталога и конфигурация адаптера закрепляются при создании диалога. Второй клиент не меняет эту связку: несовместимое подключение отклоняется. Обновлённая конфигурация применяется к новым диалогам.

Схемы протокола и каталога берутся из зафиксированных официальных исходников. TypeBox используется для собственных контрактов, а не для ручного пересказа A2UI. Настройки Ajv соответствуют dialect этих схем. Произвольные схемы от клиента или модели не компилируются как доверенная конфигурация.

Модуль применения сообщений не использует DOM. Он хранит поверхности, компоненты и модели данных, применяет операции выбранной версии и проверяет ограничения каталога. Если готовая библиотека позволяет использовать этот механизм без рендерера, это проверяется интеграционным примером; иначе реализуется небольшой модуль с проверками по официальным примерам. Поддерживаемые операции и ограничения должны быть перечислены явно.

Нельзя отклонять корректный промежуточный шаг A2UI только потому, что весь экран ещё не собран. Проверки следуют жизненному циклу протокола. При этом ссылка действия пользователя должна разрешаться в уже сохранённый компонент с объявленным действием. Счётчик `uiRevision` относится ко всему диалогу; любое принятое изменение UI делает старую форму устаревшей. Это намеренно простое правило первой версии.

Для восстановления сервер сериализует сохранённое состояние в последовательность инициализации поверхностей и данных. Клиент сначала очищает прежний экземпляр рендерера. Проверка восстановления должна сравнивать видимый результат и работу действий, а не только равенство JSON.

Уже принятые пакеты UI не откатываются при последующей ошибке или отмене. Действия разрешены только в свободном диалоге, последний запуск которого завершился успешно; после ошибки или отмены пользователь может продолжить новым текстовым запросом.

Клиентская оболочка показывает состояние запуска и отключает действия при занятости, ошибке или отмене. Сервер выполняет такие же проверки независимо от оболочки. Несохранённые изменения полей не включаются в серверный снимок; при восстановлении клиент явно сообщает об их сбросе.

## SSE и клиентский модуль

Сохранённое событие содержит `dialogId`, `seq`, `type`, `createdAt`, при необходимости `runId`, а для UI также `uiRevision`. Полезная нагрузка A2UI передаётся внутри события собственного API без подмены версии протокола. Основные типы: `run.queued`, `run.running`, `run.succeeded`, `run.failed`, `run.cancelled`, `message.text`, `ui.updated`. Ошибка завершения включается в `run.failed`.

SSE `id` равен `seq` внутри выбранного диалога. При первом подключении используется `after`, при автоматическом переподключении — валидный `Last-Event-ID`, если он присутствует. Отрицательный, неверный или опережающий историю курсор отклоняется. Клиент не переносит курсор между диалогами.

Снимок читается в согласованной транзакции и включает состояние UI, его `uiRevision`, состояние запуска и `throughSeq`. Восстановление не вызывает агента. Автоматическое удаление событий в первую версию не входит; для будущего компактирования потребуется отдельный контракт восстановления. SSE читает события строго после курсора из PostgreSQL. Уведомление в памяти лишь ускоряет чтение, периодический опрос БД закрывает потерю уведомлений и гонку между чтением истории и подпиской.

Клиент применяет события по порядку, игнорирует дубликаты и сохраняет курсор только после успешного применения. Если рендерер не смог применить пакет, клиент останавливает применение потока и выполняет восстановление со снимка. Повторный сбой восстановления показывает ошибку совместимости; бесконечного цикла переподключения нет. Новая страница без сохранённого UI начинает со снимка, даже если известен старый курсор.

Текст и UI передаются сохранёнными фрагментами, а не отдельными токенами. SSE heartbeat отправляется периодически. Объём буфера медленного клиента ограничен: при превышении соединение закрывается, клиент дочитывает события из БД. Reverse proxy отключает буферизацию SSE. Истечение пользовательской сессии закрывает поток; после повторного входа клиент восстанавливает состояние.

Клиентский модуль содержит HTTP-вызовы, подписку, отмену, дедупликацию и восстановление. Он не зависит от Lit; интеграцию снимка и событий с конкретным рендерером выполняет веб-клиент.

## Доступ и секреты

OIDC-токены остаются на сервере; браузер получает HttpOnly-cookie с подходящими Secure/SameSite-настройками. Проверяются state, nonce, issuer, audience и сроки действия средствами OIDC-библиотеки; для потока кода применяется PKCE. Все изменяющие запросы защищены от CSRF. Сессия имеет конечный срок действия, выход отзывает её на сервере.

При каждом обращении проверяется владелец диалога. Права на инструмент определяются серверной конфигурацией и пользователем; сама возможность вызвать имя из A2UI или JSON не является разрешением. В первую версию не входят сторонние недоверенные расширения и пользовательские ключи провайдеров.

Авторизацию Codex CLI оператор настраивает отдельно от OIDC приложения: через поддерживаемый CLI способ входа или учётные данные автоматизации. Служебный профиль не использует личную конфигурацию текущего разработчика. Секреты CLI, MCP-токены и секреты интеграций передаются через ограниченное окружение или механизм секретов развёртывания. Они не попадают в образ, клиентскую сборку, каталог компонентов, аргументы модели и обычные логи. Полные промпты и результаты инструментов по умолчанию не логируются. Пользовательская история и записи вызовов имеют те же ограничения доступа, что и диалог.

## Проверки и критерии поставки

| Уровень | Что проверяется |
| --- | --- |
| Vitest | Переходы статусов, лимиты, применение пакетов UI, исправление ошибки, контракт host/adapter |
| Testcontainers + PostgreSQL | Конкурентные команды, уникальность запуска, транзакции UI/событий, порядок `seq`, восстановление после перезапуска |
| Playwright | Вход, форма и действие, устаревший UI, перезагрузка страницы, SSE, снимок и реальное отображение |
| Реальный Codex CLI-адаптер | Запуск процесса, JSONL, вызов MCP, итоговый A2UI, исправление и остановка дерева процессов |

Обязательные сценарии перед первой поставкой:

- Два одновременных запроса с одним `commandId` создают один запуск; повтор после потери HTTP-ответа возвращает прежний `runId`.
- Одинаковый ключ с другим телом отклоняется; новая команда занятому диалогу не создаёт скрытого задания.
- Чужие история, снимок, поток событий и отмена недоступны по подставленному ID.
- Две вкладки отправляют действие одной ревизии: принимается только допустимое действие, остальные получают явный конфликт.
- Корректные пакеты перед ошибочным сохраняются; ошибочный пакет не меняет UI частично; повторная ошибка завершает запуск.
- Отмена во время вызова инструмента блокирует дальнейшие вызовы и поздние изменения UI. Гонка отмены и завершения имеет один терминальный результат.
- После падения `running` не запускается повторно автоматически, а `queued` остаётся доступным к выполнению.
- Событие, сохранённое перед падением, доставляется после восстановления; дубликаты не применяются дважды.
- Изменение между чтением снимка и подключением SSE не теряется; восстановленный интерфейс сохраняет действия и данные.
- Несовместимые протокол/каталог и неподдерживаемые возможности отклоняются явно.

Дополнительно проверяются недоступность shell и посторонних MCP, отказ с чужим или отозванным токеном запуска, отсутствие вызовов инструментов на исправлении, неверный JSONL, ненулевой exit code, отсутствие финального файла и завершение дочерних процессов при падении сервера.

Основные тесты воспроизводимы без платной модели через тестовый адаптер и локальный OIDC-провайдер. Парсер и управление процессом проверяются также с локальным имитатором CLI. Реальный Codex проверяется отдельно с явно настроенными авторизацией и лимитами; такой прогон обязателен для заявления о работоспособности эталонного адаптера.

CI выполняет проверку типов, форматирования, тесты и сборку отдельной job. Публикация и развёртывание зависят от её успеха. Поставка включает образ, миграции, пример конфигурации, точные версии и инструкции запуска. README получает команду запуска только после её проверки на чистой установке.

В развёртывании reverse proxy завершает TLS и обслуживает клиент и API на одном origin. PostgreSQL не публикуется наружу. Перед обновлением выполняются резервная копия и миграции; одновременный запуск несовместимых версий приложения не поддерживается. Состояние диска контролируется отдельно: отсутствие автоматического удаления истории требует следить за её ростом.

## Этапы реализации

1. **Интеграционный пример.** Закрепить версии и каталог, проверить Codex CLI → MCP-инструмент → A2UI → Lit → действие, включая ошибку и восстановление. Условие перехода: реальный браузерный сценарий воспроизводим, ограничения библиотек записаны.
2. **Ядро и хранение.** Создать схемы команд/событий/адаптера, таблицы, переходы, дедупликацию, применение UI и тестовый адаптер. Условие перехода: конкурентные запросы и сбои проверены на PostgreSQL.
3. **Приложение первой версии.** Соединить API, OIDC, SSE, MCP, Codex CLI-адаптер и веб-клиент. Условие перехода: эталонный сценарий и обязательные проверки проходят.
4. **Поставка.** Подготовить Compose, миграции, ограничения, резервное копирование и инструкцию. Условие завершения: установка с нуля и восстановление данных проверены.

## Дальнейшее развитие

| Возможность | Когда добавлять | Обязательные условия |
| --- | --- | --- |
| Отдельный worker и несколько экземпляров | Одного процесса недостаточно по нагрузке или изоляции | Lease с heartbeat, поколения исполнителей, проверка поздних записей, восстановление |
| Redis и BullMQ | Нужен отдельный брокер доставки заданий | Transactional outbox, устойчивая идентификация задания, повторная доставка, Redis без вытеснения заданий |
| Внешние MCP-сервисы и публичный MCP endpoint | Нужен источник данных или клиент за пределами установки | Отдельная внешняя авторизация и политики; внутренний endpoint для Codex уже входит в первую версию |
| Изменяющие инструменты | Появился сценарий изменения внешних данных | Подтверждения, идемпотентность внешних операций, сверка неизвестного результата |
| Другие CLI- и API-адаптеры | Появился второй конкретный агент | Проверка общего контракта, возможностей, изоляции и управления контекстом |
| Несколько организаций | Есть потребность обслуживать независимых арендаторов | Модель ролей, квоты и изоляция; RLS как дополнительная защита |
| Файлы и S3 | Вложения нужны пользовательскому сценарию | Проверка доступа, ограничения, сроки хранения и резервное копирование |
| OpenTelemetry, Prometheus, Grafana | Логов и простых метрик недостаточно | Корреляция HTTP/run/tool, политика чувствительных данных |
| Kubernetes и Changesets | Нужны кластерная поставка и отдельные публичные пакеты | Проверенные образы, миграции и матрица совместимости |

Для будущей очереди создание запуска и запись outbox выполняются одной транзакцией PostgreSQL. Повторная доставка не должна повторять завершённую операцию. Номер поколения защищает серверные записи, но сам по себе не останавливает действие во внешней системе: для изменяющих инструментов нужны отдельные ключи идемпотентности и сверка результата.

Публикация MCP за пределы приватной установки потребует отдельного решения по авторизации удалённых клиентов. Внутренний токен запуска Codex не является готовым публичным OAuth-контрактом. Подключение внешних MCP-серверов добавляет серверу роль MCP-клиента и не должно обходить существующие проверки инструментов.

Изменяющие инструменты вводятся отдельным расширением модели состояния: `awaiting_approval` удерживает диалог до решения или таймаута, `needs_reconciliation` — до проверки результата. Подтверждение относится к неизменяемому вызову, повторная доставка решения не выполняет его заново. Отмена уже начавшейся внешней операции требует описать реальный результат; статус `cancelled` не обещает откат.

Поддержка выполнения произвольного кода агентом остаётся отдельным расширением. Первая версия использует Codex для работы с контекстом, разрешёнными MCP-инструментами и A2UI; доступ к shell и редактирование проектов пользователя в этот сценарий не входят.
