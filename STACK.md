# Текущий стек и контракты

Этот документ описывает код первой версии, а не проект будущего SDK. Идея и сценарии — в [README.md](README.md), подключение приложения — в [docs/INTEGRATION.md](docs/INTEGRATION.md), HTTP и SSE — в [docs/API.md](docs/API.md). Версии зависимостей определяются `package.json` и lockfile.

## Обязательное ядро

Один Node.js-процесс, PostgreSQL и выбранный адаптер. Для настоящего Codex нужен отдельно установленный CLI и заранее авторизованный служебный профиль. Redis, BullMQ, Kubernetes, S3 и внешний брокер не используются.

| Область        | Реализация                                                                                    |
| -------------- | --------------------------------------------------------------------------------------------- |
| Среда          | Node.js 24+, TypeScript strict с запуском `.ts` без emit, pnpm 12.14.0                        |
| HTTP           | Fastify 5, TypeBox, автоген OpenAPI 3.0.3, Swagger UI 6.1.2, cookie-сессия, SSE               |
| Хранение       | PostgreSQL (в примере и CI — 18), `pg`, Drizzle; критические транзакции — SQL                 |
| Авторизация    | OIDC через `openid-client`, PKCE/state/nonce; отдельный локальный demo-вход                   |
| UI             | A2UI `v0.9.1`, официальный валидатор `@a2ui/web_core@0.14.0`, AJV 2020 для редактируемых схем |
| Клиент примера | Lit, `@a2ui/lit@0.14.0`, Vite; локальный IBM Plex Sans                                        |
| Агент          | Официальный `@openai/codex-sdk@0.163.0` и Codex CLI 0.163.0                                   |
| Инструменты    | Официальный MCP SDK, `POST /internal/mcp`, Zod-схемы аргументов                               |
| Проверки       | Vitest; PostgreSQL для storage/HTTP; браузер и платный агент проверяются отдельно             |
| Поставка       | Исходники, локальный Compose и Dockerfile демки; на Страже только CI                          |

Репозиторий `private: true`. Опубликованных adapter-sdk, storage-sdk и npm-пакета сервера нет. Общие модули переиспользуются из checkout с сохранением относительных путей.

## Жизненный цикл

Собственная точка входа вызывает `startServer` из `server/index.ts`: миграции → advisory lock → listener → Engine. Ошибка старта закрывает ресурсы. `close()` идемпотентен, снимает обработчики сигналов и закрывает Fastify/Store; потеря lock останавливает приложение. Helper обрабатывает SIGINT/SIGTERM, если не задано `handleSignals: false`. Низкоуровневый `buildApp` оставляет этот порядок вызывающему коду. Пример полного кода — в [INTEGRATION.md](docs/INTEGRATION.md).

Блокировка PostgreSQL допускает одного исполнителя для БД. Это не кластер worker-процессов с lease. При получении блокировки ранее `running` запуски становятся `failed/interrupted`, `queued` остаются в очереди. Внутренний thread Codex не восстанавливается.

## HTTP и документация

OpenAPI собирается `@fastify/swagger` из зарегистрированных маршрутов с метаданными `schema` в `server/openapi.ts`. TypeBox-схемы тел общие с contracts; схемы ответов используются сериализатором Fastify. `/openapi.json` и `/docs/json` содержат тот же документ, `/docs/yaml` — YAML; `@fastify/swagger-ui` обслуживает `/docs/` локальными ресурсами. Включены 19 публичных операций, ответы/ошибки, session cookie, CSRF и SSE. Служебный MCP и файлы документации скрыты. `pnpm openapi` выводит JSON в stdout без чтения env-файла, подключения БД и вызова модели. Работа с авторизацией из Swagger описана в [API.md](docs/API.md#swagger-и-экспорт).

## Хранение и команды

Реальные таблицы: `migrations`, `dialogs`, `runs`, `commands`, `dialog_events`, `messages`, `tool_calls`, `sessions`, `login_attempts`. Отдельных `projects`, `users` и `dialog_ui` нет. Владелец — строковый `user_id`; для OIDC он составляется из issuer и subject. UI, каталог и `task_state` хранятся в строке диалога. Публичного API обновления `taskState` пока нет; демка использует `{}`.

Команда идентифицируется парой `(user_id, commandId)`. В транзакции проверяются повтор и fingerprint, владелец и активный запуск. Повтор с другим содержимым даёт `command_conflict`. Частичный уникальный индекс запрещает два `queued/running` запуска одного диалога. При взятии задания создаётся новое `generation`; поздний ответ с неактивным поколением отклоняется.

`Store.complete` блокирует диалог, проверяет запуск, применяет A2UI к копии и одной транзакцией сохраняет UI, текст, финальный статус и события. Счётчик `seq` увеличивается под той же блокировкой. UI не публикуется до commit. SSE читает сохранённые события: отдельного transactional-outbox worker нет.

## Выполнение и отмена

```text
queued → running → succeeded | failed | cancelled
queued → cancelled
```

Число ожидающих/работающих запусков ограничено `MAX_USER_PENDING_RUNS` на пользователя (по умолчанию 10) и `MAX_PENDING_RUNS` на всю БД (100). Приём сообщений/генераций сериализуется одной транзакционной advisory lock; повтор принятой команды не занимает место. Переполнение даёт 429 `queue_limit` или `global_queue_limit`. Параллелизм процесса задаётся `MAX_CONCURRENT_RUNS` (1–8, по умолчанию 2), общий дедлайн — `RUN_TIMEOUT_MS` (100–600000 мс, по умолчанию 120000). Планировщик проверяет очередь каждые 200 мс.

Отмена сначала фиксирует статус, затем отзывает токен и передаёт AbortSignal. Поздние ответы не меняют UI и не начинают новые инструменты. Инструмент получает `context.signal` того же запуска и должен передавать его отменяемым операциям. Обработчик, игнорирующий сигнал, или удалённый провайдер могут продолжить работу/тарификацию. Готового отката внешних действий нет.

## Контракт адаптера

Источник истины — `server/adapters/types.ts`:

```text
// AgentAdapter: цикл инструментов принадлежит готовому агенту.
run(context, callTool, signal): Promise<{ text: string; a2uiJson: string }>

// ModelAdapter: цикл принадлежит runAdapter, не более 8 шагов.
step(context, results, signal): Promise<
  | { type: "output"; output: { text: string; a2uiJson: string } }
  | { type: "tool_calls"; calls: { id: string; name: string; args: unknown }[] }
>
```

`AgentContext` включает запуск, диалог, историю, taskState, снимок каталога, инструкции, URL/token инструментов и при необходимости `repair`. Codex превращает его в текст через `preparePrompt`; другой адаптер получает объект и сам организует передачу своему API. Методов `describe`, `host.emitText`, `host.proposeUi` и каталога capabilities нет. Экземпляр передаётся в `options.adapter`; переменная `ADAPTER` только в `demo/server/config.ts` выбирает `codex | fixture`. Общий config не содержит Codex-настроек; их проверяет `codexOptionsFrom`. Метаданные API получают `options.adapterName` (по умолчанию `adapter.kind`).

`a2uiJson` — строка с массивом сообщений, не объект `{messages:…}` и не HTML. SDK ограничивает внешнюю оболочку `{text,a2uiJson}`, а сервер отдельно разбирает строку и проверяет A2UI. Пример допустимого результата:

```ts
const output = {
  text: "Готово",
  a2uiJson: JSON.stringify([
    {
      version: "v0.9.1",
      createSurface: {
        surfaceId: "answer",
        catalogId:
          "https://a2ui.org/specification/v0_9/catalogs/basic/catalog.json",
      },
    },
    {
      version: "v0.9.1",
      updateComponents: {
        surfaceId: "answer",
        components: [{ id: "root", component: "Text", text: "Результат" }],
      },
    },
  ]),
};
```

При SyntaxError или ошибке проверки UI со статусом 422 Engine допускает одну попытку исправления в пределах исходного дедлайна. Старый токен отзывается; MCP не подключается, `callTool` запрещён. Повторная ошибка завершает запуск, прежний UI сохраняется, отвергнутый текст ассистента в историю не попадает. Пустой массив `[]` допустим для текстового ответа без изменения UI.

## Codex

`server/adapters/codex/index.ts` использует `Codex.startThread().runStreamed()`. Каждый запуск — свежий `codex exec`, включая исправление; история берётся из PostgreSQL, а не через resume thread. Официальный SDK разбирает JSONL. Служебный `codex-process.mjs` добавляет `--ephemeral`, `--ignore-user-config`, `--ignore-rules`, output schema и надзор за процессами.

Разрешены только MCP-инструменты `project` текущего запуска. Shell, file changes, web search, apps и делегирование отключены; неожиданные события инструментов отклоняются. Среда CLI собирается явно: секреты БД и произвольное окружение сервера не наследуются. Базовые инструкции находятся в `server/prompt.ts`, прикладные — в `options.instructions`/`PROJECT_INSTRUCTIONS_FILE`. AGENTS.md проекта не является промптом этого изолированного Codex.

По умолчанию суммарный сырой stdout/stderr ограничен 512000 байт, итоговый ответ — 128000 байт, поле `text` — 12000 символов. Runtime создаётся в отдельных каталогах под `os.tmpdir()/a2ui-codex`. Для иной среды задайте `CodexOptions.runtimeDir` или `CODEX_RUNTIME_DIR`, читаемую `codexOptionsFrom`. Отдельная ручная очистка завершённых runtime имеет dry-run и выключена по умолчанию; профиль CLI обслуживается отдельно. Остановка группы процессов проверена на Linux; отдельного Windows-прогона не было.

## Каталог и проверка UI

[Каталог](catalog/README.md) содержит Text, Column, Row, Button, TextField, Divider, Card. При старте собирается документ с общими определениями и скомпилированными AJV-схемами. Снимок, версия, профиль и SHA-256 закрепляются в диалоге/генерации. Сервер проверяет результат по сохранённому документу, а не по текущим файлам; кэш валидаторов учитывает содержимое.

Проверки включают размер/глубину JSON, массив сообщений `v0.9.1`, схемы компонентов, официальный MessageProcessor с strict validation, существование поверхностей, ссылки от `root`, циклы, допустимые пути и действия. Пределы: до 32 сообщений в пакете, 128000 символов сериализованного JSON, до 8 поверхностей, 200 компонентов на поверхность. Клиентские функции, `validationRegexp`, шаблонные дети и опасные ключи запрещены. JSON Schema, SDK-модель и renderer должны оставаться совместимыми.

`createCatalogProfile(document, model)` проверяет JSON-схемы и собирает снимок. `options.catalogs` регистрирует пары ID/profile → SDK-модель, первый профиль становится стандартным. При завершении Store выбирает модель по сохранённому профилю; при её отсутствии возвращает `unsupported_catalog`. Встроенный Basic остаётся доступен для прежних диалогов. JSON-документ сам по себе не устанавливает реализацию. Пример собственной схемы/модели/Lit-компонента — [custom-catalog](examples/custom-catalog/README.md).

`packages/catalogs` поддерживает local/HTTPS/MCP, кэш и явный `refresh`. Конфигурация источника задаётся оператором; HTTP endpoint для обновления отсутствует. При зарегистрированных профилях `configuredCatalog` принимает документ совпадающего ID/profile и проверяет схемы по соответствующей модели. Без них допускается только точное совпадение ID/digest встроенного Basic. Несовместимые изменения SDK-модели требуют нового профиля и сохранения прежней реализации для старых диалогов.

## Обслуживание данных

Миграция 0004 добавляет `dialogs.updated_at`, `commands.created_at/expired` и индексы. `Store.maintenance` по умолчанию только показывает план; ненулевой TTL истории удаляет неактивный диалог целиком, сохраняя tombstone команд до истечения их собственного TTL. Это даёт 410 на повтор удалённой операции в пределах дедупликации. Сроки и периодический запуск выключены по умолчанию; каждый проход ограничен batchSize и защищён отдельной транзакционной lock. Автообслуживание `startServer` касается только БД. `pnpm maintenance` также умеет планировать/выполнять ручную очистку завершённых runtime Codex. Точные параметры и ограничения — в [OPERATIONS.md](docs/OPERATIONS.md).

## Инструменты

`ToolDefinition` — `description`, Zod-схема объекта и `execute(args, context)`. Реестр передаётся приложением; MCP объявляет его инструменты читающими. Сервер проверяет имя, аргументы, активность запуска и идентичность повторного вызова. До 12 записей вызовов на запуск; аргументы ограничены 16000 символов сериализованного JSON. Результаты и статусы хранятся в `tool_calls`; отдельных tool-событий SSE нет.

`ToolContext` содержит readonly userId/dialogId/runId/signal. Владелец извлекается по активному запуску из PostgreSQL для прямого вызова и MCP. Обработчик проверяет доступ к предметному ресурсу по этому контексту; пользовательские аргументы не подменяют владельца. Контекст организации, внешние записи и подтверждения требуют отдельной реализации. MCP каталога и MCP инструментов — два независимых подключения с разными полномочиями.

## Что ещё не реализовано

Настоящий API-адаптер модели; несколько исполнителей/организаций; автоматическая загрузка плагинов; потоковая публикация токенов/A2UI; другая библиотека renderer; готовые предметные ACL и подтверждения записей; публичный taskState API; пагинация истории; автоматический деплой. Это направления развития, а не доступные методы.

Актуальные результаты прогонов — в [docs/VALIDATION.md](docs/VALIDATION.md), устройство CI — в [docs/CI.md](docs/CI.md).
