# Подключение к своему проекту

Сейчас сервер подключается из исходников. Корневой пакет имеет `private: true`; опубликованного npm-пакета, команды `create` и загрузки плагинов по имени нет. Используйте собственный checkout или fork с закреплённым commit. Сохраните вместе `server/`, `packages/`, `catalog/`, `package.json` и lockfile: между ними есть относительные импорты.

Есть два варианта: подключить свой фронтенд к работающему HTTP-серверу или собрать собственное приложение через `buildApp`. Если запустить штатные `pnpm start` / `make run`, получится демоприложение ламп, а не пустой универсальный сервер.

## Своя серверная точка входа

Пример ниже предполагает папку `project/` в корне этого checkout. Она относится к вашему приложению; в репозитории готового `project/main.ts` нет. Зависимости устанавливаются командой `pnpm install --frozen-lockfile` из корня.

Создайте `project/main.ts`:

```ts
import { z } from "zod";
import { startServer, configFrom } from "../server/index.ts";
import type { ToolRegistry } from "../server/index.ts";
import {
  codexAdapter,
  codexOptionsFrom,
} from "../server/adapters/codex/index.ts";

const tools: ToolRegistry = {
  get_server_uptime: {
    description: "Время работы процесса приложения в секундах",
    schema: z.object({}).strict(),
    execute: async (_args, context) => {
      context.signal.throwIfAborted();
      return { seconds: Math.floor(process.uptime()) };
    },
  },
};

const server = await startServer(configFrom(process.env), {
  adapter: codexAdapter(codexOptionsFrom(process.env)),
  adapterName: "codex",
  tools,
  instructions: `Ты помощник оператора. Отвечай по-русски.
Для времени работы вызывай get_server_uptime, не придумывай результат.
Верни text и a2uiJson — строку с массивом сообщений A2UI v0.9.1.
Используй каталог из контекста. У каждой поверхности корень id=root.
Для результата достаточно Text. При замене поверхности сначала удали прежнюю.
При ошибке источника объясни её и верни a2uiJson="[]".`,
  logger: true,
});
// SIGINT/SIGTERM обрабатываются автоматически.
// Для программной остановки: await server.close();
```

`startServer` выполняет миграции, получает блокировку единственного исполнителя, открывает listener, запускает Engine и закрывает ресурсы при ошибке. `close()` идемпотентен и освобождает блокировку. Потеря блокировки останавливает приложение. Для встраивания в существующий процесс задайте `handleSignals: false` и вызывайте `close` из его жизненного цикла; при необходимости используйте `onLockLost`. Helper владеет Store и закрывает его, включая явно переданный `options.store`.

Низкоуровневый `buildApp` остаётся для Fastify inject и собственного lifecycle. При его использовании сохраните порядок `startEngine: false` → миграции → блокировка → listener → Engine; сам `buildApp` не запускает миграции и не получает lock.

Для статического фронтенда передайте `webRoot` с абсолютным путём к сборке. Без него API работает, но страница `/` не обслуживается. Можно оставить отдельный dev-сервер с proxy, как в `demo/web/vite.config.ts`.

Swagger доступен на `/docs/` независимо от `webRoot`; спецификация собирается автоматически на `/openapi.json`, а `pnpm openapi` экспортирует её без запуска БД/агента. Используйте документацию на том же origin, что и клиент; в dev-примере Vite проксирует `/docs` и OpenAPI вместе с API. Вход, автоматический CSRF и правила Try it out — в [API.md](API.md#swagger-и-экспорт).

Создайте свой `project/.env`, не добавляя его в Git:

```dotenv
HOST=127.0.0.1
PORT=3100
PUBLIC_URL=http://localhost:3100
DATABASE_URL=postgres://USER:PASSWORD@127.0.0.1:5432/PROJECT_DB
AUTH_MODE=demo
CODEX_BIN=codex
CODEX_PROFILE_DIR=/absolute/path/to/service-codex-profile
```

Подставьте существующую отдельную БД и заранее авторизованный служебный профиль. `AUTH_MODE=demo` даёт общую локальную учётную запись и допустим только на loopback. Для пользователей собственной установки выберите OIDC; параметры и запуск CLI описаны в [demo/README.md](../demo/README.md). Запускайте из корня:

```sh
node --env-file=project/.env project/main.ts
```

Для своей папки добавьте её в `tsconfig.json` и в команды форматирования, если продолжаете разработку в этом checkout. Корневые скрипты сейчас проверяют только перечисленные в них каталоги.

## Инструменты и права

`ToolRegistry` передаётся в options `startServer`/`buildApp`. У каждого инструмента есть `description`, Zod-схема объекта и `execute(args, context)`. Аргументы проверяются сервером; результат должен быть сериализуемым JSON. Вызовы записываются в PostgreSQL и связываются с активным запуском. Пример реального приложения — `demo/server/tools.ts`.

Внутренний `POST /internal/mcp` создаётся сервером. Codex получает URL и короткоживущий bearer token только своего запуска. Токен не передаётся браузеру и отзывается перед исправлением ответа, при отмене и завершении. Внешний MCP-инструментарий автоматически не импортируется: для внешнего API напишите свой обработчик.

`ToolContext` содержит readonly `userId`, `dialogId`, `runId` и `signal`. Владелец определяется по активному запуску в БД, а не аргументам агента; это одинаково для прямого вызова и MCP. В обработчике фильтруйте данные по `context.userId`, проверяйте доступ к конкретному ресурсу и передавайте `context.signal` в fetch/запросы, поддерживающие отмену. Доверенный ID не реализует предметные ACL автоматически. Готового механизма подтверждения записей и контекста организации нет; MCP пока объявляет инструменты читающими. Пример личных данных — [notes](../examples/notes/README.md).

## Авторизация существующего проекта

Для собственной сессии задайте `AUTH_MODE=custom` и `options.auth`. Этот режим требует серверного `AuthProvider.resolve(request)`; без него запуск завершится ошибкой. OIDC/demo продолжают работать без custom provider.

Пример `project/auth.ts` для уже существующего хранилища сессий:

```ts
import type { AuthProvider, AuthSession } from "../server/index.ts";

export function applicationAuth(
  lookup: (cookie: string) => Promise<AuthSession | undefined>,
  revoke: (cookie: string) => Promise<void>,
): AuthProvider {
  return {
    resolve: (request) => lookup(request.cookies.app_session ?? ""),
    login: (_request, reply) => reply.redirect("/login"),
    async logout(request, reply) {
      await revoke(request.cookies.app_session ?? "");
      reply.clearCookie("app_session", { path: "/" });
    },
  };
}
```

Реализуйте lookup/revoke через авторитетное хранилище вашего приложения, затем передайте результат factory в `options.auth`. `AuthSession` содержит `userId`, `name`, серверный `csrf` и `expiresAt: Date`. Неверная или просроченная сессия не даёт доступа. Header/query `userId` от клиента не является проверкой личности.

Проверки Origin и CSRF действуют и в custom-режиме. Существующее приложение должно создавать/хранить CSRF-токен с сессией; клиент получает его через `/v1/session`. SSE повторно вызывает resolve при работе соединения, поэтому отзыв/истечение сессии закрывает подписку. `login` и `logout` необязательны: при обращении к отсутствующей операции API возвращает 501, а не имитирует вход/отзыв. Внешний backend может использовать свои маршруты входа.

Образец `examples/notes` демонстрирует это с непрозрачной cookie и двумя учебными пользователями; его вход разрешён только локально. В тестах приложение запускается из отдельной временной папки вне checkout и выполняет запрос → инструмент → UI → действие → восстановление.

## Инструкции и каталог

`AGENTS.md` читает агент-разработчик, который интегрирует сервер. Запускаемый приложением Codex работает с `--ignore-rules`: правила из соседнего `AGENTS.md` автоматически не становятся его промптом.

Инструкции прикладного агента задаются через `options.instructions`; текст из `PROJECT_INSTRUCTIONS_FILE` добавляется к ним при старте. Базовая упаковка ответа находится в `server/prompt.ts`, предметный пример — в `demo/server/instructions.ts`. Укажите задачи, разрешённые инструменты, реакцию на ошибку источника и правила создания/замены поверхностей. Сервер добавляет каталог, текущий UI, историю и команду. Секреты в инструкции не включайте.

Схемы компонентов редактируются в [catalog/](../catalog/README.md), отдельно от предметных инструментов. Текущий клиент поддерживает семь компонентов Basic Catalog. Новый JSON не реализует новый тип на фронтенде. После правок выполните `make test-components`, пересоберите клиент и перезапустите сервер. Новые диалоги получат новый снимок, старые сохранят свой; совместимость их рендеринга при обновлении клиента проверяет разработчик приложения.

Для собственного набора создайте `createCatalogProfile(document, sdkModel)` и передайте `catalogs: [profile]` в `startServer`/`buildApp`. Документ содержит `catalogId`, `version`, `profile`, `components`, `common`, `$defs`; SDK-модель — `Catalog` из закреплённого `@a2ui/web_core/catalog` с тем же ID и Zod-схемами свойств. Первый профиль становится стандартным для новых диалогов; прежние совместимые профили регистрируйте далее в массиве. Дубликаты ID/profile запрещены. Без `catalogs` остаётся встроенный Basic. `CATALOG_SOURCE_CONFIG` выбирает документ local/HTTPS/MCP зарегистрированного профиля; без регистрации требуется точное совпадение с Basic по ID/digest.

Клиент регистрирует свой renderer с тем же catalogId и сверяет профиль снимка. Схемы остаются закреплёнными в диалоге, серверная модель выбирается по его ID/профилю. При несовместимом изменении модели нужен новый `profile`; старую модель и клиентскую реализацию сохраняйте для прежних диалогов. Без зарегистрированной модели новый результат такого диалога отклоняется с `unsupported_catalog`. Полный пример схемы, SDK-модели, Lit-компонента и preview — [examples/custom-catalog](../examples/custom-catalog/README.md). Общие ограничения статического профиля сохраняются: регистрация не включает функции или произвольный код агента.

## Свой фронтенд

Используйте один origin для страницы, `/auth` и `/v1`: разместите клиент в `webRoot` или настройте proxy. Клиент сейчас использует относительные URL, cookie-сессию и `credentials: same-origin`; CORS и авторизация API-ключом не реализованы. `PUBLIC_URL` должен совпадать с адресом страницы, включая порт. `localhost` и `127.0.0.1` — разные origins.

`packages/client/src/index.ts` предоставляет `Client`. Сессия и разовая генерация доступны через `request`/`command`, диалог — через `create`, `message`, `snapshot`, `watch`, `action`, `cancel`. Это транспорт; A2UI он не рисует. Для Lit подключите `@a2ui/lit/v0_9` и `@a2ui/web_core/v0_9` из закреплённых зависимостей; готовый пример интеграции рендерера — `demo/web/src/app.ts`.

Последовательность для диалога:

1. Получить `GET /v1/session`. Если пользователь не вошёл — направить на `/auth/login` (OIDC) либо вызвать `/auth/demo` локально. Затем перечитать сессию и установить `client.csrf`.
2. Создать диалог и прочитать снимок. Сверить `protocol`, `catalogId`, `profile` с клиентом.
3. В новом/очищенном renderer применить весь `snapshot.dialog.ui.messages`. Запомнить `ui.revision` и `throughSeq`.
4. Подписаться на события начиная с `throughSeq`. `ui.updated.payload.ui` — полный собранный UI, поэтому заменять состояние рендерера, а не добавлять снимок к прежнему. Порядок событий, восстановление и ошибки — в [API.md](API.md).
5. Отправить сообщение. Действие рендерера преобразовать в `{ surfaceId, componentId, name, context }` и отправить с актуальной `uiRevision`. Блокировать действия старой/неактивной формы.
6. При разрыве последовательности событий заново получить снимок и подписку. При смене диалога закрывать прежнюю подписку, при выходе очищать историю и UI в памяти.

Пример транспортной части в браузере после входа:

```ts
import { Client } from "../packages/client/src/index.ts";

const client = new Client();
const session = await client.request<{ authenticated: boolean; csrf?: string }>(
  "/v1/session",
);
if (!session.authenticated || !session.csrf) throw new Error("Сначала войдите");
client.csrf = session.csrf;
const { dialogId } = await client.create();
await client.message(dialogId, "Сколько времени работает сервер?");
const snapshot = await client.snapshot(dialogId);
// Здесь подключите renderer и watch по последовательности выше.
```

Путь импорта предполагает ваш клиентский файл в `project/`; сборщик должен поддерживать TypeScript. Полные HTTP-тела, статусы и события описаны в [API.md](API.md), а не выводятся из этого короткого примера.

## Другой адаптер

Контракты находятся в `server/adapters/types.ts`. `AgentAdapter.run(context, callTool, signal)` возвращает `{ text, a2uiJson }`; `ModelAdapter.step` возвращает итог либо запросы инструментов. Для модели сервер выполняет цикл до восьми шагов, готовый агент ведёт его сам. Все вызовы должны соблюдать `AbortSignal`. На `context.repair` инструменты недоступны.

Передавайте экземпляр через `options.adapter`, метку для API — через `options.adapterName`; по умолчанию метка равна `adapter.kind`. Динамического обнаружения адаптеров нет. Общий `configFrom` не проверяет настройки провайдера: для Codex вызывайте `codexOptionsFrom`. `ADAPTER=codex|fixture` относится только к `demo/server/config.ts`. Методами `describe`, `host.emitText` или `host.proposeUi` код сейчас не располагает. Для текстового промпта можно переиспользовать `server/prompt.ts`; сторонний адаптер сам решает, как передать `AgentContext` своему провайдеру.

## Когда подключение проверено

До использования в приложении подтвердите вход, запрос → инструмент → принятый A2UI, действие формы → обновление, восстановление страницы, отмену и отказ для чужого диалога. Некорректный JSON/A2UI должен получить одну попытку исправления; повторная ошибка сохраняет прежний UI. Команды проверки и границы уже выполненных прогонов — в [VALIDATION.md](VALIDATION.md).

Для эксплуатации выберите общую/пользовательскую квоту очереди и срок хранения. Очистка выключена по умолчанию; сначала проверьте `pnpm maintenance` без `--apply`. Настройки, tombstone команд и отдельная очистка runtime — в [OPERATIONS.md](OPERATIONS.md).

Сейчас это основа для интеграции в одном процессе. Распределённые исполнители, контекст организаций и готовые предметные ACL, согласование записывающих действий, пагинация истории и автоматический деплой ещё требуют работы. Нельзя считать их готовыми только по наличию общего HTTP API.

## Указатель для агента в другом репозитории

Если сервер подключён соседним checkout или вложен в `vendor/`, агент вашего проекта может не получить его AGENTS.md автоматически. Добавьте в AGENTS.md приложения явный указатель, заменив путь на свой:

```text
При работе с A2UI-интеграцией сначала прочитай
vendor/A2UI-uniserver/AGENTS.md и docs/INTEGRATION.md внутри этого checkout.
Используй закреплённый commit сервера и текущие типы его исходников.
Подключай предметные инструменты и инструкции в точке сборки приложения;
изменение общего ядра согласуй отдельно от интеграции клиента.
```

Это инструкции агенту-разработчику. Промпт прикладного агента по-прежнему задаётся через серверные options/файл инструкций.
