# Очередь и хранение данных

Сервер по-прежнему рассчитан на один процесс-исполнитель на PostgreSQL. Общая квота ограничивает приём работы, а retention задаёт срок хранения. Это разные настройки: квота не удаляет историю, чтение истории не продлевает её срок хранения.

## Ограничения очереди

| Переменная              | По умолчанию | Назначение                                     |
| ----------------------- | ------------ | ---------------------------------------------- |
| `MAX_PENDING_RUNS`      | 100          | Все `queued` и `running` запуски в БД, 1–10000 |
| `MAX_USER_PENDING_RUNS` | 10           | Те же запуски одного пользователя, 1–1000      |
| `MAX_CONCURRENT_RUNS`   | 2            | Параллелизм исполнителя, 1–8                   |
| `RUN_TIMEOUT_MS`        | 120000       | Общий дедлайн запуска и исправления            |

Приём сообщений и разовых генераций проходит одну транзакционную блокировку PostgreSQL. Одновременные запросы разных пользователей не могут превысить общую квоту. Повтор уже принятой команды не занимает ещё одно место. Отказ возвращает HTTP 429: `queue_limit` для пользователя или `global_queue_limit` для всей очереди; не сохраняет новую команду/генерацию. После освобождения места запрос можно повторить с тем же UUID. Клиенту стоит делать паузу между повторами; `Retry-After` пока не выдаётся.

`RUN_TIMEOUT_MS` ограничивает ожидание асинхронного адаптера, исправления и инструментов, даже если они игнорируют AbortSignal. По дедлайну токен отзывается, запуск становится `failed/run_timeout`, слот освобождается; поздние результаты и попытки вызвать инструмент не меняют состояние. Отмена пользователем сохраняет статус `cancelled`.

При `close()` адаптер получает сигнал остановки и до двух секунд на завершение, после чего сервер перестаёт ждать его Promise. Активный запуск получает `failed/interrupted`; очередь сохраняется. При включённом `handleSignals` SIGINT/SIGTERM после закрытия ресурсов завершают процесс, включая оставленные обработчиком таймеры/сокеты. Во встраиваемом приложении задайте `handleSignals:false`: завершением процесса и чужими ресурсами управляет приложение.

Это ограничение ожидания асинхронной операции. Произвольный код внутри процесса нельзя принудительно прервать таким способом: инструмент должен передавать signal своему I/O, синхронная блокировка event loop требует изоляции исполнителя. Завершение локального процесса не откатывает уже отправленное действие удалённому сервису.

## Retention в PostgreSQL

| Переменная                | По умолчанию | Назначение                                                            |
| ------------------------- | ------------ | --------------------------------------------------------------------- |
| `HISTORY_RETENTION_DAYS`  | 0            | Неактивные диалоги и генерации; 0 — хранить бессрочно                 |
| `COMMAND_RETENTION_DAYS`  | 0            | Журнал дедупликации команд; 0 — хранить бессрочно                     |
| `MAINTENANCE_INTERVAL_MS` | 0            | Период очистки в `startServer`; 0 — выключена, иначе 1000–86400000 мс |

Сроки задаются целыми днями до 3650. Ненулевой срок команд должен быть не меньше срока истории. При обновлении существующей БД миграция 0004 устанавливает `updated_at` старых диалогов в момент миграции: они не попадают под очистку сразу из-за старого `created_at`.

Активность диалога — последнее сохранённое событие, включая постановку запроса и завершение. Чтение снимка/SSE не обновляет `updated_at`. Диалоги с `queued/running` не удаляются даже при старой метке. История удаляется целиком: UI, каталог, сообщения, события, запуски и результаты инструментов. Частичного удаления событий с разрывом `seq` нет. После удаления ресурс возвращает 404; открытый SSE закрывается. Периодическая очистка удаляет максимум 100 диалогов за проход, поэтому срок не гарантирует мгновенного удаления.

Команды удалённого диалога превращаются в tombstone без прежнего результата. Пока запись дедупликации существует, точный повтор возвращает **410 `command_expired`**, а не создаёт новое задание. Другой запрос с этим UUID по-прежнему даёт `command_conflict`. После удаления самой записи по `COMMAND_RETENTION_DAYS` сервер уже не помнит UUID: старый повтор может стать новой командой. Клиенту нужно ограничить срок повторов этим горизонтом и создавать новые UUID для новых операций.

Также очищаются истёкшие встроенные `sessions` и `login_attempts`, по 100 записей каждого вида. Хранилище custom-авторизации обслуживает само приложение. Действующие сессии и команды активных запусков сохраняются. Одновременный maintenance возвращает `busy: true`; блокировка, выборка и изменения происходят в одной транзакции. Между интервалами нет перекрывающихся проходов; `close()` дожидается текущего.

## Предварительный просмотр и ручной запуск

Сначала примените миграции обычным запуском сервера или `pnpm db:migrate`. Команда обслуживания сама схему не меняет. С выбранной БД и настройками из `demo/.env`:

```sh
pnpm maintenance
```

Это **dry-run**: JSON содержит ID/счётчики кандидатов, записи и файлы остаются на месте. Даже при нулевых сроках он показывает истёкшие auth-записи. Чтобы применить согласованную политику:

```sh
pnpm maintenance --apply
```

Для отдельного приложения используйте его env-файл и тот же скрипт, например из корня checkout:

```sh
node --env-file=project/.env scripts/maintenance.ts
# Добавьте --apply после проверки плана.
```

При программном использовании: `await store.maintenance({historyDays:30, commandDays:60, batchSize:100, dryRun:true})`. Уберите dry-run только после выбора политики хранения. HTTP endpoint обслуживания нет. Периодический режим `startServer` включается отдельно и выполняет изменения без предварительного просмотра; низкоуровневый `buildApp` таймер не запускает.

## Временные файлы Codex

Runtime может содержать входные и выходные данные агента. Задайте отдельный закрытый `CODEX_RUNTIME_DIR`; он не должен содержать служебный профиль `CODEX_PROFILE_DIR` или находиться внутри него. По умолчанию используется `os.tmpdir()/a2ui-codex`.

`CODEX_RUNTIME_RETENTION_DAYS=0` отключает очистку файлов. Положительное значение (1–3650) включает её **только в ручной команде maintenance**; серверный таймер обслуживает БД. Сначала запускайте dry-run. За один вызов выбирается до 100 папок `run-*` с обычным старым `process.json`, содержащим `done: true`. Незавершённые, недавние и повреждённые записи, символические ссылки и посторонние имена пропускаются. Корень `/`, сам домашний/временный каталог, вложение профиля и runtime и symlink runtime отклоняются. Перед удалением состояние проверяется повторно; используется `rm -r -- <путь>` без shell.

Держите runtime доступным только учётной записи сервиса. Это очистка завершённых запусков, не восстановление после аварии: оставшиеся `done: false` требуют отдельной проверки оператором. Файлы профиля CLI и его авторизации эта команда не обслуживает. `--apply` необратим: предварительный просмотр показывает кандидатов на момент запуска и не является резервной копией.
