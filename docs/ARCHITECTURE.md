# Границы реализации

Сервер связывает клиент, адаптер, каталог и инструменты. Он сохраняет и проверяет A2UI JSON; отображение выполняет renderer на клиенте. Список файлов и технические ограничения — в [STACK.md](../STACK.md), подключение собственного приложения — в [INTEGRATION.md](INTEGRATION.md).

## Сборка приложения

`server/index.ts` экспортирует `startServer` для полного lifecycle и `buildApp(config, options)` для низкоуровневой сборки. Приложение передаёт `adapter`, необязательные `tools`, `instructions`, `webRoot` и параметры запуска; получает `{app,store,engine}`. `server/start.ts` отвечает за миграции, блокировку, listener и остановку. `demo/server/app.ts` собирает options примера, его `main.ts` вызывает общий helper. Конфигурация ядра отделена от Codex и выбора адаптера демки.

Общее ядро не импортирует каталог товаров, fixture, веб-клиент или инструкции демки. `packages/core` проверяет UI и действия, `packages/contracts` задаёт типы и HTTP-схемы, `packages/client` реализует браузерный транспорт. Данные и оформление нового проекта остаются в его точке сборки и клиенте. Это исходники одного checkout, а не набор опубликованных пакетов.

`server/openapi.ts` связывает схемы запросов/ответов с описаниями операций, security и генератором. Маршруты `app.ts`/`auth.ts` подключают эти схемы; Fastify использует их для обработки HTTP, `@fastify/swagger` — для автогенерации спецификации. Swagger UI `/docs/` работает без клиентской сборки, `scripts/openapi.ts` экспортирует JSON без запуска БД/агента. Для деталей и входа через UI прочитайте [API.md](API.md#swagger-и-экспорт).

Режим `AUTH_MODE=custom` подключает `options.auth`: серверный `resolve` проверяет существующую сессию проекта и возвращает userId/name/csrf/expiresAt. Отсутствующий или просроченный результат не даёт доступа. Общие проверки владельца, CSRF, Origin и повторная проверка сессии SSE сохраняются; служебный MCP по-прежнему использует токен запуска.

## Владельцы контекста и цикла

Engine собирает `AgentContext`: запуск, диалог, taskState, историю, UI, закреплённый каталог и инструкции. Состояние задачи отдельно от UI, но готового HTTP API для его изменения нет. Codex использует `server/prompt.ts` для текстовой упаковки; новый адаптер сам передаёт этот контекст своему провайдеру.

Контракт `kind: model` вызывает `step` и выполняет предложенные инструменты до восьми шагов. Контракт `kind: agent` вызывает `run`; готовый агент ведёт собственный цикл. Codex обращается к инструментам через MCP, второй серверный цикл вокруг него не запускается. Реального API-адаптера модели пока нет, контракт проверяется тестами.

Для каждой команды Codex создаёт свежий ephemeral thread. История и UI восстанавливаются из PostgreSQL; внутренний thread CLI не служит хранилищем разговора. Приложение задаёт инструкции через `options.instructions` и `PROJECT_INSTRUCTIONS_FILE`. AGENTS.md относится к агенту-разработчику и автоматически изолированным CLI не читается.

## Каталог

[Редактируемый источник](../catalog/README.md) находится в `catalog/`: метаданные, отдельные схемы, общие определения и примеры. Загрузчик собирает документ и компилирует JSON Schema AJV без скачивания внешних `$ref`. Ошибочная схема останавливает запуск.

`packages/catalogs` предоставляет реестр, local/HTTPS/MCP-загрузчики, кэш и явный `refresh`. Оператор выбирает источник в конфигурации; браузер и агент не выбирают произвольный URL. Приложение регистрирует SDK-модели через `createCatalogProfile` и `options.catalogs`; первый профиль используется для новых диалогов. Внешний документ должен соответствовать зарегистрированному ID/profile и пройти проверку схем. Без регистрации действует точное совпадение ID/digest встроенного Basic. Административного endpoint обновления нет.

Снимок документа, версия, профиль и SHA-256 сохраняются при создании диалога/генерации. Агент получает этот снимок, а `Store.complete` проверяет свойства компонентов по нему же с соответствующей SDK-моделью. Кэш валидаторов зависит от содержания схем. Перезапуск применяет изменения файлов к новым диалогам; старые сохраняют свой документ. Совместимость нового клиента со старыми снимками нужно проверять отдельно. Свой компонент требует модели и renderer, как в [примере StatusBadge](../examples/custom-catalog/README.md).

## MCP каталога и инструментов

MCP-загрузчик каталога читает описание интерфейса от имени оператора. Служебный `/internal/mcp` предоставляет инструменты активному запуску по короткоживущему токену. Это независимые подключения с отдельными настройками и credentials.

Один `ToolRegistry` передаётся Engine и его MCP-шлюзу. Проверяются имя, схема аргументов, активность запуска и повтор вызова. Обработчик `execute(args, context)` получает владельца активного запуска из БД, dialogId/runId и сигнал отмены. Реестр общий для процесса, поэтому обработчик фильтрует личные данные по context.userId и проверяет доступ к каждому ресурсу. Прямые вызовы и MCP используют одну проверку. Подтверждение записей и организации ещё требуют доработки.

## Приём ответа и действия

Engine разбирает `a2uiJson`. Store проверяет активное поколение запуска и атомарно применяет пакет: структуру сообщений `v0.9.1`, схемы компонентов закреплённого каталога, официальный валидатор, ограничения профиля, поверхности, пути, ссылки и циклы. Лишь после успешной проверки сохраняются UI, текст и статус. При синтаксической ошибке JSON или ошибке UI 422 допускается одна попытка исправления с отозванным токеном и без инструментов. Повторная ошибка сохраняет прежний UI.

Действие клиента содержит диалог, поверхность, компонент, имя, контекст и `uiRevision`. Сервер сверяет достижимость компонента и статические значения с сохранённым UI; привязанные значения полей остаются недоверенным вводом. Неактивная или устаревшая форма не запускает агента. Проверка события не заменяет проверку доступа к предметным данным.

## Сохранение и доставка

PostgreSQL хранит команды, запуски, историю, UI, каталог и упорядоченные события. Команды повторяются с тем же UUID, события — читаются после `seq`. Транзакция результата сохраняет изменения и события вместе; SSE читает журнал после commit. `ui.updated` содержит полный UI, не дельту. Клиент заменяет состояние renderer и восстанавливает снимок при разрыве последовательности. Токены модели и промежуточный A2UI не стримятся.

Диалог поддерживает следующие сообщения и действия. Разовая генерация — отдельное сохранённое задание без продолжения, с теми же владельцем, дедупликацией, исполнителем и лимитами. Форматы — в [API.md](API.md).

## Эксплуатация и проверка

Одна advisory lock PostgreSQL допускает один сервер-исполнитель на БД. При перезапуске `running` становятся `interrupted`, очередь сохраняется. Несколько worker, broker и автоматический перенос исполнения не реализованы. Локальные профили — в [demo/README.md](../demo/README.md); Страж выполняет [только CI](CI.md).

Общая и пользовательская квоты учитывают `queued/running` обоих режимов; приём сериализуется отдельной транзакционной lock. Политика хранения выключена по умолчанию. Maintenance блокирует и удаляет только неактивные диалоги целиком, оставляет tombstone команд и отдельно ограничивает срок дедупликации. Dry-run доступен через CLI и Store; таймер `startServer` запускается только по явной настройке. Завершённый runtime Codex очищается отдельным ручным проходом. Подробности — в [OPERATIONS.md](OPERATIONS.md).

Тесты отдельно проверяют каталог, протокол, контракт адаптеров, CLI-процессы, PostgreSQL и HTTP. Доказательства реального агента/браузера и границы готовности — в [VALIDATION.md](VALIDATION.md).
