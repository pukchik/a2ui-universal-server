# HTTP API и события

Контракт реализован в `server/app.ts`, `server/auth.ts` и `packages/contracts/src/index.ts`. `/openapi.json` содержит зарегистрированные JSON-схемы запросов, но не полное описание SSE, всех ответов и авторизации. Этот документ дополняет его. Клиент и API работают на одном origin; подробности подключения — в [INTEGRATION.md](INTEGRATION.md).

## Сессия

| Маршрут              | Результат                                                                        |
| -------------------- | -------------------------------------------------------------------------------- |
| `GET /health`        | `{ok:true,version:"0.1.0"}`; это liveness, не проверка БД или модели             |
| `GET /v1/config`     | `protocol`, `catalogId`, `profile`, настроенная метка `adapter`                  |
| `GET /v1/session`    | `authenticated`, `authMode`, `adapter`; после входа ещё `userId`, `name`, `csrf` |
| `GET /auth/login`    | Начать OIDC-вход                                                                 |
| `GET /auth/callback` | OIDC callback; зарегистрировать у провайдера `${PUBLIC_URL}/auth/callback`       |
| `POST /auth/demo`    | Локальный вход только при `AUTH_MODE=demo`; нужен совпадающий `Origin`           |
| `POST /auth/logout`  | Отозвать серверную сессию; нужны cookie, CSRF и Origin                           |

Во встроенных OIDC/demo-режимах браузер получает HttpOnly cookie `a2ui_session`, `SameSite=Lax`, срок — 8 часов. На HTTPS cookie имеет `Secure`. Все операции с диалогами и генерациями проверяют владельца; ID ресурса не является разрешением. Для POST передавайте `Origin`, cookie и `X-CSRF-Token` из `/v1/session`. Браузер сам формирует Origin; серверный HTTP-клиент должен задать его явно. OIDC-токен не является встроенным bearer token этого API.

При `AUTH_MODE=custom` приложение передаёт серверный `AuthProvider`; cookie и хранение сессии принадлежат ему. `/v1/session` возвращает `authMode: "custom"` и тот же CSRF-контракт. Отсутствующий login/logout handler возвращает 501 (`login_not_supported` / `logout_not_supported`). Демо-вход и OIDC callback в этом режиме отключены. Пример bridge — в [INTEGRATION.md](INTEGRATION.md#авторизация-существующего-проекта).

## Команды диалога

| Метод и путь                              | Тело / ответ                                            |
| ----------------------------------------- | ------------------------------------------------------- |
| `GET /v1/dialogs`                         | Список диалогов пользователя, без одноразовых генераций |
| `POST /v1/dialogs`                        | `{commandId}` → `201 {commandId,dialogId}`              |
| `GET /v1/dialogs/:id`                     | Диалог, UI, каталог, текущий запуск                     |
| `GET /v1/dialogs/:id/messages`            | История сообщений                                       |
| `GET /v1/dialogs/:id/snapshot`            | Согласованный снимок и курсор событий                   |
| `POST /v1/dialogs/:id/messages`           | `{commandId,text}` → `202 {commandId,dialogId,runId}`   |
| `POST /v1/dialogs/:id/actions`            | Тело ниже → `202 {commandId,dialogId,runId}`            |
| `POST /v1/dialogs/:id/runs/:runId/cancel` | `{commandId}` → `200 {commandId,runId,status}`          |

`commandId` создаётся клиентом как UUID до отправки. Повтор того же ID и тела тем же пользователем возвращает прежний результат принятия; другое содержимое даёт `409 command_conflict`. Повтор не запускает агента заново. Не создавайте новый ID для сетевого повтора. `Client.retry()` сохраняет исходный ID, но только пока экземпляр клиента жив; долговременного хранилища pending-команд у него нет.

`text` — непустая после обрезки строка, до 12 000 символов. Для диалога разрешён один `queued`/`running` запуск. Статус ответа `202` означает принятие; окончательный результат читается из снимка или событий.

Пример отправки действия, а не непосредственного вызова инструмента:

```json
{
  "commandId": "c3dc0867-ae03-4dc8-a4dc-5f951e942fe6",
  "uiRevision": 1,
  "action": {
    "surfaceId": "products",
    "componentId": "button-lamp-1",
    "name": "show_product",
    "context": { "productId": "lamp-1" }
  }
}
```

Сервер сверяет поверхность, достижимый от `root` компонент, имя события и статические значения контекста с сохранённым UI. Значения полей с привязкой `{path:"/field"}` остаются пользовательским вводом. Требуются актуальная `uiRevision` и последний запуск со статусом `succeeded`; старые и неактивные формы отклоняются. Имя события не обязывает агента вызывать одноимённый инструмент: это новая команда в контексте диалога.

## Снимок и SSE

Снимок имеет структуру:

```text
{
  dialog: { id, ui: { messages, revision }, run, catalog, /* … */ },
  messages: [/* история текста */],
  throughSeq: 5,
  protocol: "v0.9.1",
  catalogId: "https://a2ui.org/specification/v0_9/catalogs/basic/catalog.json",
  profile: "basic-static-0.14.0-v1"
}
```

`dialog.ui.messages` — полный принятый UI. Это отдельное поле от истории `messages`. Версия каталога, документ и SHA-256 находятся в `dialog.catalog`. `throughSeq` соответствует тому же снимку; чтение событий начинают после него.

`GET /v1/dialogs/:id/events?after=<throughSeq>` возвращает `text/event-stream`. `Last-Event-ID`, если передан, имеет приоритет над `after`. Строка `id:` содержит `seq`, `data:` — JSON события `{dialogId,seq,type,runId?,payload,createdAt}`. Именованных SSE `event:` нет: используйте `onmessage`. Комментарии heartbeat не являются событиями приложения.

| `type`                                                        | `payload`                                        |
| ------------------------------------------------------------- | ------------------------------------------------ |
| `run.queued`, `run.running`, `run.succeeded`, `run.cancelled` | `{runId}`                                        |
| `run.failed`                                                  | `{code,message}`                                 |
| `message.text`                                                | `{text}` — принятый итоговый текст ассистента    |
| `ui.updated`                                                  | `{ui:{messages,revision}}` — полный собранный UI |

События вызовов инструментов в SSE сейчас не публикуются. Их аргументы, результаты и статусы хранятся в `tool_calls`; результат возвращается агенту, а не напрямую браузеру.

Игнорируйте события другого диалога и номера `seq <=` уже применённого. При пропуске номера восстановите снимок и подписку. `Client.watch` проверяет непрерывность и вызывает `onReset`; обработчик должен сам перечитать снимок. `EventSource` переподключается, но разрыв соединения не отменяет запуск. SSE проверяет сессию и закрывается после её истечения. При замене UI очищайте/пересоздавайте renderer; повторное добавление полного снимка к старому состоянию создаёт конфликт поверхностей. Пример — `resetRenderer` в `demo/web/src/app.ts`.

Потока токенов или постепенно принимаемых фрагментов A2UI сейчас нет. `message.text` и `ui.updated` публикуются при сохранении проверенного итогового ответа.

## Разовая генерация

| Метод и путь                      | Тело / ответ                                              |
| --------------------------------- | --------------------------------------------------------- |
| `POST /v1/generations`            | `{commandId,text}` → `202 {commandId,generationId,runId}` |
| `GET /v1/generations/:id`         | Тот же формат снимка с `dialog.mode="generation"`         |
| `POST /v1/generations/:id/cancel` | `{commandId}` → результат отмены                          |

Это отдельное сохраняемое задание без продолжения истории другого диалога. Оно не попадает в `/v1/dialogs`; сообщение или действие для продолжения возвращает `generation_is_one_shot`. Для простого клиента опрашивайте GET до терминального статуса `succeeded | failed | cancelled`. Специального `/v1/generations/:id/events` нет.

## Ошибки и ограничения

HTTP-ошибка имеет вид `{error:{code,message}}`. Поля `details` нет. Ошибка уже принятого запуска находится в `dialog.run.error` и `run.failed`; успешный HTTP POST не гарантирует успешный запуск.

| Код                                                                       | Что делать клиенту                                                            |
| ------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `login_required` (401)                                                    | Войти заново                                                                  |
| `csrf` (403)                                                              | Проверить Origin, cookie и перечитать сессию                                  |
| `not_found` (404)                                                         | Не показывать чужой/недоступный ресурс                                        |
| `command_conflict` (409)                                                  | Не использовать один UUID для разных команд                                   |
| `dialog_busy` (409)                                                       | Дождаться завершения или отменить текущий запуск                              |
| `stale_ui`, `ui_inactive` (409)                                           | Восстановить снимок; не повторять старое действие автоматически               |
| `queue_limit` (429)                                                       | Дождаться освобождения очереди пользователя                                   |
| `invalid_ui`, `invalid_component`, `missing_component`, `component_cycle` | Ошибка результата агента; после неудачного исправления прежний UI сохраняется |
| `context_limit`, `run_timeout`, `interrupted`                             | Начать новый диалог / повторить осмысленной новой командой                    |

Пользователь может иметь до 10 ожидающих/выполняющихся запусков; параллелизм процесса задаётся `MAX_CONCURRENT_RUNS` (1–8). `RUN_TIMEOUT_MS` ограничивает весь запуск вместе с исправлением. Общей квоты всех пользователей, пагинации истории и автоматической очистки данных пока нет. Подробные ограничения UI и адаптеров — в [STACK.md](../STACK.md).

`/internal/mcp` — отдельный служебный POST с токеном активного запуска. Пользовательская cookie и OIDC-токен туда не подходят; браузерные Origin отклоняются. GET/DELETE этого endpoint возвращают 405.
