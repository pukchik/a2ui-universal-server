# CI в Gitea

Workflow `.gitea/workflows/ci.yml` запускается на push в `main` и вручную через Actions. На общем runner со связью с сетью хоста проверяется только доверенный код; автоматического запуска для внешних pull requests нет.

Две job с явной зависимостью:

1. `tests`: установка из lockfile, форматирование, синтаксис служебного shell-скрипта, TypeScript и полный Vitest с отдельной PostgreSQL 18.
2. `build`: только после успешной `tests`, свежий checkout её точного SHA, повторная установка из lockfile и production-сборка клиента.

PostgreSQL ставится из официального PGDG-репозитория внутри временного job-контейнера. Для каждого прогона `scripts/test-ci.sh` создаёт отдельный кластер и БД, выключает TCP, подключает тесты через Unix-сокет и останавливает сервер при выходе. Производственная БД и секреты приложения не нужны. Скрипт не удаляет существующие базы или каталоги. Runtime-данные остаются внутри временного контейнера и не попадают в кэш.

Кэшируются только скачанные пакеты pnpm. Ключ учитывает проект, ОС/архитектуру, Node.js, версию pnpm и lockfile; установка всегда выполняется с `--frozen-lockfile`. Jobs работают и без кэша. Кэш runner проверен включённым на Страже; Node.js-образ закреплён digest. PostgreSQL устанавливается только в `tests`; общий образ runner ради проекта не изменяется. Повторная установка apt-пакетов остаётся затратой подготовки job; отдельный готовый CI-образ можно согласовать, если замеры покажут необходимость.

Настоящий Codex и браузерные сценарии проверяются отдельно: CI не получает авторизацию модели и не расходует её лимиты. Docker-образ в этом workflow не собирается: runner не получает Docker socket. Проверка контейнерного запуска остаётся отдельной от `pnpm build`.

## Проверенные прогоны на Страже

До добавления интеграционного API, 21 октября 2026 года [запуск 107](https://home.eralas.ru/git/eralash/A2UI-uniserver/actions/runs/107) на commit `d5445d1` завершился успешно: 97 тестов в 6 файлах, затем сборка того же SHA. `tests` заняла 51 секунду, `build` — 24 секунды. Включены отдельные проверки компонентов из `catalog/` и адаптера `server/adapters/codex/` с имитатором `tests/fixtures/codex.mjs`; настоящий агент не запускается.

При первоначальной настройке в [запуске 99](https://home.eralas.ru/git/eralash/A2UI-uniserver/actions/runs/99) `tests` получила cache miss и сохранила кэш pnpm около 192 МБ, а зависимая `build` восстановила его с cache hit. Установка зависимостей заняла 11,5 секунды без кэша и 4,8 секунды после восстановления; само восстановление добавило около 7 секунд. Это исторические замеры работы кэша, не обещание времени каждого запуска. PostgreSQL тогда устанавливалась 13 секунд; workflow продолжает устанавливать её только в `tests`.

После добавления custom auth, ToolContext, startServer и внешнего приложения [запуск 109](https://home.eralas.ru/git/eralash/A2UI-uniserver/actions/runs/109) на `d4ba527` прошёл 112 тестов в 9 файлах и зависимую сборку. `tests` заняла 55 секунд, `build` — 23 секунды.

С профилями каталогов, квотами и retention [запуск 110](https://home.eralas.ru/git/eralash/A2UI-uniserver/actions/runs/110) на `307fbca` прошёл 128 тестов в 12 файлах и зависимую сборку. С OpenAPI/Swagger локальный набор вырос до 132 тестов в 13 файлах. Workflow запускает все `tests/**/*.test.ts`, включая новые; изменения workflow не потребовались. Retention проверяется только на БД временного кластера, удаление файлов runtime — с подставным runner. Текущий результат push проверяйте в [Actions](https://home.eralas.ru/git/eralash/A2UI-uniserver/actions).

Зависимость `needs: tests` и порядок jobs проверены. Намеренно ломающий тестовый commit не публиковался; отдельного эксперимента с отказом всего workflow не было.

## Почему пока без CD

Workflow выполняет только `tests` и `build`. По решению владельца одноразовый fixture-стенд убран из проекта и отключён на Страже. Автопубликации больше нет; для работы с Codex предусмотрен локальный `make run`.

До включения CD нужно сверить текущий шлюз со всеми требованиями приложения: один origin и абсолютные пути `/auth`/`/v1`, writable runtime Codex, служебная авторизация, PostgreSQL и передача роли единственного исполнителя между релизами. Сам CI зависимости приложения не развёртывает. Совместимость развёртывания по подпути сейчас не подтверждена.

Перед изменением workflow или деплоя заново прочитайте полные текущие [DEPLOYMENT.md](https://home.eralas.ru/deploy-docs/DEPLOYMENT.md) и [CICD_SKILL.md](https://home.eralas.ru/deploy-docs/CICD_SKILL.md), как требует [AGENTS.md](../AGENTS.md). Будущий `deploy` должен зависеть от проверок и публиковать тот же проверенный commit; credentials доступны только шагу публикации.
