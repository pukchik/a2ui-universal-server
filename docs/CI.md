# CI в Gitea

Workflow `.gitea/workflows/ci.yml` запускается на push в `main` и вручную через Actions. На общем runner со связью с сетью хоста проверяется только доверенный код; автоматического запуска для внешних pull requests нет.

Две независимые job:

1. `tests`: установка из lockfile, форматирование, синтаксис служебного shell-скрипта, TypeScript и полный Vitest с отдельной PostgreSQL 18.
2. `build`: только после успешной `tests`, свежий checkout её точного SHA, повторная установка из lockfile и production-сборка клиента.

PostgreSQL ставится из официального PGDG-репозитория внутри временного job-контейнера. Для каждого прогона `scripts/test-ci.sh` создаёт отдельный кластер и БД, выключает TCP, подключает тесты через Unix-сокет и останавливает сервер при выходе. Производственная БД и секреты приложения не нужны. Скрипт не удаляет существующие базы или каталоги. Runtime-данные остаются внутри временного контейнера и не попадают в кэш.

Кэшируются только скачанные пакеты pnpm. Ключ учитывает проект, ОС/архитектуру, Node.js, версию pnpm и lockfile; установка всегда выполняется с `--frozen-lockfile`. Jobs работают и без кэша. Кэш runner проверен включённым на Страже; Node.js-образ закреплён digest. PostgreSQL устанавливается только в `tests`; общий образ runner ради проекта не изменяется. Повторная установка apt-пакетов остаётся затратой подготовки job; отдельный готовый CI-образ можно согласовать, если замеры покажут необходимость.

Настоящий Codex и браузерные сценарии проверяются отдельно: CI не получает авторизацию модели и не расходует её лимиты. Docker-образ в этом workflow не собирается: runner не получает Docker socket. Проверка контейнерного запуска остаётся отдельной от `pnpm build`.

## Почему пока без CD

По решению владельца сначала включён CI. Для CD на Страже ещё нужны регистрация проекта, project-scoped `STRAZH_DEPLOY_TOKEN`, PostgreSQL, OIDC и служебная авторизация Codex. Workflow не пытается публиковать приложение с отсутствующими зависимостями.

До включения CD также нужно согласовать совместимость с текущим шлюзом: путь `/test/PROJECT/` для клиента, API, redirects и cookies; writable runtime вне read-only root/noexec `/tmp`; передача служебного профиля; передача роли исполнителя между старым и новым релизом при сохранённой блокировке PostgreSQL. Штатный протокол не запускает PostgreSQL/Compose и не поддерживает произвольные mounts. Эти ограничения нельзя обходить из job.

Актуальный контракт: [инструкция Стража](https://home.eralas.ru/deploy-docs/DEPLOYMENT.md). Будущий `deploy` должен зависеть от всех проверок и публиковать тот же проверенный commit; credentials доступны только шагу публикации.
