# Демоприложение A2UI

В этой папке собран пример каталога ламп: Lit-клиент в `web/`, данные, инструменты, тестовый адаптер и инструкции агенту в `server/`, проверка Codex в `scripts/`, конфигурации Keycloak и каталога в `deploy/`. Здесь же находятся `.env`, Makefile, Compose и Dockerfile. Пример использует общее серверное ядро из `../server` и пакеты из `../packages`; папка не является отдельным репозиторием.

Можно работать непосредственно отсюда:

```sh
cd demo
make run       # Codex
# или make demo — тестовый адаптер
```

Команды из корня (`make run`, `make demo`) перенаправляются в этот Makefile. Оформление клиента описано в [DESIGN.md](DESIGN.md). Для своего приложения используйте [инструкцию подключения](../docs/INTEGRATION.md): штатная точка входа запускает именно этот пример, а не пустой сервер. Адаптер находится в `server/adapters/codex/` от корня checkout.

Нужны Node.js 24+, pnpm 12.14.0 и PostgreSQL 18. Официальный `@openai/codex-sdk@0.163.0` устанавливается вместе с зависимостями; Codex CLI 0.163.0 нужен для реального агента. Установка зависимостей закреплена lockfile.

```sh
pnpm install --frozen-lockfile
cp demo/.env.example demo/.env
```

В `demo/.env` укажите `DATABASE_URL` и параметры авторизации. Все команды pnpm и Docker выполняются из корня репозитория. Команды Make доступны как из корня, так и из `demo/`. Миграции автоматически применяются через общий `startServer`; отдельно их можно выполнить через `pnpm db:migrate`. Выбор адаптера и его окружение проверяет `demo/server/config.ts`, общие серверные настройки — `server/config.ts`.

## Команды Make

```sh
make setup    # pnpm install и создание demo/.env без перезаписи существующего
make db       # PostgreSQL из compose, с ожиданием готовности
make run      # сборка + Codex + локальный вход, http://localhost:3100
```

До `make run` задайте `DATABASE_URL` и `CODEX_PROFILE_DIR` в `demo/.env`; профиль Codex должен быть заранее авторизован. Команда принудительно выбирает `ADAPTER=codex`, `AUTH_MODE=demo` и `HOST=127.0.0.1`. Кнопка «Открыть демонстрацию» даёт локальную сессию приложения; запросы обрабатывает настоящий Codex и расходует лимиты выбранной учётной записи. Это запуск для разработки на своём компьютере. `PUBLIC_URL` должен соответствовать адресу браузера и указывать на loopback. Для внешней PostgreSQL пропустите `make db`.

| Команда                   | Назначение                                                                |
| ------------------------- | ------------------------------------------------------------------------- |
| `make run` / `make codex` | Собрать клиент и запустить локальный Codex без OIDC                       |
| `make start`              | Собрать клиент и запустить сервер с настройками `demo/.env`, включая OIDC |
| `make demo`               | Собрать и запустить локальную демку с fixture-адаптером, без модели       |
| `make dev` / `make web`   | Сервер с перезапуском / отдельный Vite; параметры берутся из `demo/.env`  |
| `make check`              | Форматирование и TypeScript                                               |
| `make test`               | Vitest; полный прогон требует отдельной `TEST_DATABASE_URL`               |
| `make test-components`    | 53 проверки схем и примеров UI, без PostgreSQL и модели                   |
| `make smoke-codex`        | Настоящий запрос и действие через Codex, с отдельной БД                   |

`make run`, `make start` и `make demo` работают на переднем плане; остановка — Ctrl+C. База и профиль не создаются и не очищаются этими командами. Все параметры можно передать через окружение или аргументы Make, например `make run PORT=3200 PUBLIC_URL=http://localhost:3200`. Эквивалентные команды pnpm остаются доступны ниже.

## Быстрая локальная демонстрация

```sh
docker compose --env-file demo/.env -f demo/compose.yaml up -d db
```

Настройки `demo/.env`:

```dotenv
DATABASE_URL=postgres://a2ui:a2ui@127.0.0.1:5432/a2ui
PUBLIC_URL=http://localhost:3100
HOST=127.0.0.1
PORT=3100
AUTH_MODE=demo
ADAPTER=fixture
```

```sh
pnpm build
pnpm start
```

Откройте **http://localhost:3100**, нажмите «Открыть демонстрацию» и отправьте запрос про лампы. `PUBLIC_URL` должен совпадать с адресом в браузере: `localhost` и `127.0.0.1` — разные origins. Демо-вход работает только на loopback. Тестовый адаптер явно отмечен в интерфейсе и не обращается к модели.

Результат содержит карточки, поле уточнения и кнопку обновления. Проверьте «Подробнее», отправку значения поля и перезагрузку страницы. Данные каталога демонстрационные, инструментов изменения нет.

Для разработки можно запустить `pnpm dev` и отдельно `pnpm web:dev`. В таком случае установите `PUBLIC_URL=http://localhost:5173`, поскольку браузер работает через Vite proxy. Для обычного запуска достаточно собранного клиента и одного процесса сервера.

## Codex CLI

Коннектор использует официальный `@openai/codex-sdk@0.163.0`: `Codex.startThread()` и `Thread.runStreamed()`. Свежий thread создаётся для каждой команды; история и UI передаются из PostgreSQL. Восстановление внутреннего thread SDK не используется.

Установите закреплённую версию CLI и подготовьте отдельный служебный профиль через поддерживаемый Codex способ авторизации. Профиль и его credentials хранятся вне репозитория. Для первоначального входа оператор может запустить `codex login` в окружении с выбранным служебным `CODEX_HOME`; приложение получает этот каталог через свою настройку `CODEX_PROFILE_DIR`.

```sh
npm install --global @openai/codex@0.163.0
CODEX_HOME=/absolute/path/to/service-codex-profile codex login
codex --version
```

Это подготовка оператора. Существующая авторизация пользователя приложения через OIDC не авторизует CLI. Сам runtime не наследует произвольные переменные окружения сервера.

```dotenv
ADAPTER=codex
CODEX_BIN=codex
CODEX_PROFILE_DIR=/absolute/path/to/service-codex-profile
RUN_TIMEOUT_MS=120000
MAX_CONCURRENT_RUNS=2
# CODEX_RUNTIME_DIR=/absolute/path/to/writable-runtime
```

Модель можно явно указать через `CODEX_MODEL`; без этой настройки используется выбор CLI. Сервер не наследует пользовательский `config.toml`, сторонние MCP, shell-окружение и секреты БД в процесс агента. Встроенные shell, web search, приложения и делегирование отключены. Агент получает только внутренний MCP проекта.

SDK запускает CLI через небольшой `codex-process.mjs`, который добавляет `--ephemeral`, `--ignore-user-config`, `--ignore-rules` и схему ответа, ограничивает сырой вывод и останавливает группу процессов при отмене. Разбор JSONL выполняет SDK; собственный парсер не используется. Каждая команда запускается через свежий `codex exec --ephemeral`; продолжение разговора строится из PostgreSQL. При ошибке A2UI разрешён один дополнительный запуск исправления без MCP. JSONL содержит служебные события, в браузер передаются проверенные результат и состояние выполнения.

Реальная проверка с настроенными `DATABASE_URL` и `CODEX_PROFILE_DIR`:

```sh
pnpm smoke:codex
```

Скрипт запускает локальный сервер на порту из `PORT` (3110, если переменная не задана; `demo/.env` может задавать 3100), проверяет MCP-поиск и итоговый A2UI, отправляет действие «Подробнее», проверяет MCP `get_product` и обновление UI, затем закрывает сервер. Используйте отдельную БД и свободный порт, например `DATABASE_URL=… PORT=3110 pnpm smoke:codex`: сервер сохраняет демонстрационный диалог и требует единственного исполнителя в этой БД. Скрипт не копирует credentials. Обращение к модели использует лимиты настроенной учётной записи.

## OIDC

Основной режим — `AUTH_MODE=oidc`. Для локального примера:

```sh
docker compose --env-file demo/.env -f demo/compose.yaml --profile oidc up -d db keycloak
```

```dotenv
AUTH_MODE=oidc
OIDC_ISSUER=http://localhost:18080/realms/a2ui
OIDC_CLIENT_ID=a2ui
OIDC_CLIENT_SECRET=local-development-secret
PUBLIC_URL=http://localhost:3100
```

Тестовый пользователь из `demo/deploy/realm.json`: `demo` / `demo-password`. Это открытые демонстрационные учётные данные только для локального примера. В собственной установке задайте свой OIDC-провайдер, клиента и секрет. Браузер получает серверную сессию, токены провайдера остаются на сервере; изменяющие HTTP-запросы требуют CSRF-токен и совпадающий Origin.

Для контейнерного сервера предусмотрен профиль `server`:

```sh
docker compose --env-file demo/.env -f demo/compose.yaml --profile server up -d --build db server
```

OIDC issuer должен быть доступен **и браузеру, и контейнеру** с тем же именем. `localhost:18080` внутри контейнера не является Keycloak на хосте. В этом профиле настройте доступный обеим сторонам issuer, `PUBLIC_URL` и существующий служебный `CODEX_PROFILE_DIR`. `init: true` обеспечивает надзор за дочерними процессами в контейнере. PostgreSQL и опубликованные порты примера привязаны к loopback; публичная установка использует TLS reverse proxy без буферизации SSE.

## Каталоги и инструкции

Редактируемый каталог UI находится в [../catalog/](../catalog/README.md). Для каждого компонента есть JSON-схема в `catalog/components/` и примеры в `catalog/examples/`; список включённых компонентов задаётся в `catalog/catalog.json`. Исходные схемы взяты из `@a2ui/web_core@0.14.0`; поддерживаемый профиль включает Text, Column, Row, Button, TextField, Divider и Card. Нет локальных функций, изображений, внешних ссылок или шаблонных списков. Проверяется официальный протокол и схемы компонентов, затем ограничения приложения и ссылки между компонентами. Один JSON нового типа не создаёт его реализацию в рендерере.

Каталог загружается один раз при запуске. Документ, версия, профиль и SHA-256 сохраняются в диалоге. Агент и серверная проверка используют один закреплённый документ. После редактирования файлов запустите `make test-components`, пересоберите клиент и перезапустите сервер. Новые диалоги получат изменения, старые сохранят свой каталог. Реестр внешних источников имеет отдельную операцию `refresh`, без запроса к источнику на каждое сообщение.

Экспорт документа для локального источника:

```sh
node scripts/export-catalog.ts > /tmp/a2ui-catalog.json
```

Локальная конфигурация источника:

```json
{
  "name": "project-components",
  "type": "local",
  "path": "/tmp/a2ui-catalog.json"
}
```

Задайте путь к ней в `CATALOG_SOURCE_CONFIG`. Другие типы — `https` с `url`, и `mcp` с `url`, `tool`, необязательными `args`. Пример MCP находится в `demo/deploy/catalog-source.example.json`. `tokenEnv` называет отдельную переменную окружения для авторизации источника; эти полномочия не передаются агенту.

Штатная демка регистрирует только встроенный профиль, поэтому её источники должны возвращать документ с теми же ID/digest. В своём приложении можно передать `options.catalogs` со схемами и SDK-моделью и подключить соответствующий renderer; пример — [custom-catalog](../examples/custom-catalog/README.md). Несовместимый документ отклоняется при старте. Частные URL и credentials регистрирует оператор; браузер и модель не могут выбирать произвольные источники.

`PROJECT_INSTRUCTIONS_FILE` позволяет подключить локальный текст инструкций проекта. Подготовка запроса собирает отдельно протокол, закреплённый каталог, инструкции, состояние задачи, UI, историю и текущую команду. При превышении лимита контекста сервер завершает запуск понятной ошибкой.

## Очередь и очистка

`MAX_PENDING_RUNS` ограничивает все ожидающие/работающие задания (по умолчанию 100), `MAX_USER_PENDING_RUNS` — пользователя (10). `HISTORY_RETENTION_DAYS`, `COMMAND_RETENTION_DAYS` и `MAINTENANCE_INTERVAL_MS` по умолчанию равны 0: история не удаляется, автоочистка выключена. `pnpm maintenance` показывает план без изменений, `--apply` применяет его. Отдельный `CODEX_RUNTIME_RETENTION_DAYS` включает ручную очистку только завершённых runtime, профиль CLI сохраняется отдельно. До включения прочитайте [правила хранения и повторов команд](../docs/OPERATIONS.md).

Общая упаковка находится в `server/prompt.ts`, инструкции этого примера — в `demo/server/instructions.ts`. Разрабатывающий интеграцию агент читает AGENTS.md; запущенный приложением Codex не использует его автоматически. Данные, инструменты и инструкции ламп заменяются в собственной точке сборки, а не редактированием общего Engine.

Пример собственного приложения с `AuthProvider`, пользовательским `ToolContext` и общим запуском находится в [examples/notes](../examples/notes/README.md).

## API

Cookie-сессия, CSRF/Origin, тела команд, ошибки, SSE и разовая генерация описаны в [docs/API.md](../docs/API.md). Обе стороны используют A2UI v0.9.1 и профиль из `catalog/catalog.json`. Swagger UI находится на `/docs/`, автоматически собранный OpenAPI со схемами запросов/ответов и авторизации — на `/openapi.json`. Vite проксирует документацию вместе с API. Экспорт без БД/модели: `pnpm openapi > /tmp/a2ui-openapi.json`. Локально войдите через POST `/auth/demo` в Swagger; для последующих POST токен CSRF подставляется из текущей сессии автоматически.

Транспорт находится в `packages/client/src/index.ts`; demo-клиент дополнительно проверяет профиль, заменяет renderer при полном UI и восстанавливает снимок при пропуске событий. Запрос не отправляет A2UI напрямую: JSON генерирует агент, сервер проверяет и сохраняет его перед доставкой.

## Проверки

```sh
pnpm check
pnpm build
pnpm test:components
pnpm test
TEST_DATABASE_URL=postgres://USER:PASSWORD@localhost:5432/a2ui_test pnpm test
```

Без `TEST_DATABASE_URL` проверки PostgreSQL и HTTP явно пропускаются; это не полный прогон. Используйте отдельную тестовую БД. Тесты создают записи с уникальными идентификаторами и не очищают существующие базы или файлы.

Проверяются каталог, границы адаптеров, официальный A2UI, повторные команды, права, отмена, восстановление после перезапуска, ошибки и остановка процесса CLI. Браузерный прогон и реальный Codex проверяются отдельно от детерминированных тестов. Результаты конкретной проверки приведены в [docs/VALIDATION.md](../docs/VALIDATION.md).
